## P1 审查结论

P1 是可安装、可调用且如实返回 `501 FEATURE_NOT_IMPLEMENTED` 的框架，而非可用的知识问答系统；不能将解析、SQLite、BM25、模型下载或真实答案的占位视为 P1 的业务成功。Contract Gate 的 schema/provider/consumer 检查、A1 的 FastAPI/CLI/SDK/离线占位、A2 的事件状态机，以及 B 的 WebUI/Widget scaffold 均可独立运行。

## P2 逐组实施分工（仅计划，不表示业务已完成）

**顺序**：本次 Contract Gate 冻结并校验共享接口 → 后端 A1/A2 各自以 fake 独立实施和验收 → 两后端完成后进行跨流真适配器检查 → 仅当用户明确宣告 A1/A2 均完成时启动 B → 最终以公开 API 做管理端联调。原总计划将 `KBManagement/indexing.py` 视作 A2 的检索/向量部分，但 P2 的增量快照事务编排、发布与失败回滚需要单一写入 owner；此处把该文件完整归 A1，A2 在 `chunking.py`/`Infrastructure/indexes.py` 提供冻结算法端口。若日后拆出纯向量算法模块，须进入下一阶段 Gate，不能两组同时改 `indexing.py`。

| 阶段/Owner | 文件和交付 | 独立退出条件 |
|---|---|---|
| **A1 后端：平台与确定性业务** | `Infrastructure/sqlite.py`、`repositories.py`、`migrations/`、`blobs.py`、`snapshots.py` 的文件/元数据职责；`KBManagement/service.py`、`content.py`、`imports.py`、`sources.py`、`parsers.py`、`versions.py`；`KBManagement/indexing.py` 的事务编排、快照发布与增量复用由 A1 独占，调用 A2 提供的切块/关键词索引端口，不直接编辑 A2 算法文件；`ServiceAPI` 普通 CRUD/upload/import/version routes、Job 通用租约/恢复与组合根、Python SDK/CLI。先做显式迁移及事务/UoW，随后内容寻址存储与各格式解析，再做上传/预览/增量、不可变快照、CAS 发布/回滚、任务租约/崩溃恢复；绝不以部分清单推断删除。 | 临时 DB/目录下用 fake reader 验证多格式/坏文件/OCR 诊断、客户端上传/服务端授权根、文档及 QA 对 CRUD、合并/镜像/部分扫描、预览变化冲突、未变化修订复用、构建失败不换活动版本、并发发布、回滚/重启/幂等。独立运行 A1 自己的测试，不等待 A2 业务实现。 |

**已执行；仅接口冻结，P2 业务仍为 501。** `Contracts/knowledge.py` 增加不可信 UploadManifest（保留客户端 selection，但不赋予删除资格）、服务端 SourceManifest（full/partial + succeeded/failed + complete）、UploadBatch、ImportPreviewRequest 与必带 expected_preview_hash 的 ImportRequest，限定路径不能遍历/使用绝对路径、已 ready/published 快照必须具备 keyword_profile/index_ref 及文档→修订映射字段。`Contracts/selection.py` 区分请求 KBTarget 与不可空、无重复的 PinnedKBTarget/ResolvedScope/SelectionResult；单库 SearchScope 明确固定 kb/version/keyword 配置，SnapshotReader 在读取快照/片段/修订时传 AccessScope。`Q&A_Assistant/retrieval.py` 的 hybrid/federated 入口显式要求 `k`，关键词构造无需向量模型/重排器。`KBManagement/sources.py`、`imports.py` 及 `Infrastructure/indexes.py`、`snapshots.py` 只是签名对齐，未引入业务成功输出。模型安装/回答仍按 P3 实现。
