## 任务一：Agent 评测用例自动化生成（冷启动数据集构建）

### 任务背景

Agent 评测决定 Agent 是否达到预定质量、是否符合上线要求，是 Agent 研发流程中不可或缺的一环。业界无论是开源项目还是闭源产品，都已提供了多种 Agent 评测器，在一定程度上提升了评测执行的效率。

但对使用者而言，评测的门槛依然很高，核心原因在于：评测器解决的是"如何执行评测"，并没有解决"评测使用什么数据"的问题——使用者仍需自行准备评测数据集。Agent 相关应用目前仍处于探索阶段，业界尚未形成统一的数据集构建方法论供使用者参考，使用者普遍不清楚一份可用的评测数据集应当包含多少用例、覆盖哪些场景与维度，也缺少便捷易用的工具来辅助完成这一过程。

与此同时，一个 Agent 或 Skill 在完成开发后，通常已经积累了可用于反推评测用例的多种信息，例如 Agent 代码、Skill 代码、Agent 执行轨迹（Trace）、需求文档、设计文档、用户指南等——这些信息目前普遍未被有效利用来辅助构建评测数据集。

落到 Agent Insight 自身的评测体系中，当前的评测数据集分为理想输出评测集、轨迹评测集与可靠性评测集三类，但准备数据项目前主要依赖人工：在数据集页面"单个添加"或"批量导入"，或对运行观测中的某条 Trace 手动执行"加入评测集"——尚不具备从代码、Trace、文档批量反推生成评测用例并给出有效性评分的能力，这也是"评估与实验"模块中冷启动门槛最高的一环。

因此，需要具备自动化生成评测用例的能力，将生成结果作为使用者的"冷启动"数据集，并可直接对接平台已有的评测数据集与评估器体系，使使用者在尚未准备任何评测数据的情况下也能快速发起评测，从而降低评测门槛、提升评测效率。

### 任务描述

需要实现 Agent 评测用例自动化生成的能力，生成范围聚焦可直接复用平台已有评测流程的理想输出评测集与轨迹评测集两类场景（依赖独立故障模式定义的可靠性评测集不在本任务范围内）；该能力需要作为 Agent Insight 平台内的功能模块落地（可新增入口/页面，或复用现有评测数据集管理流程），使平台用户能够直接在 Agent Insight 中使用，而不是停留为脱离平台的独立脚本或工具，具体需求如下：

1. **输入支持**：支持基于以下一种或多种信息源自动生成 Agent/Skill 评测用例：Agent 代码、Skill 代码（含 SKILL.md 及其 scripts、references）、Agent 执行轨迹（Trace）、相关文档（需求文档、设计文档、用户指南等）。当同时提供多种信息源时，应能够综合利用这些信息源生成用例，而不仅限于孤立处理单一来源。

2. **用例要素完整性**：生成的每条评测用例应包含开展一次评测所需的基本要素，包括但不限于评测场景/输入，以及可用于判定 Agent 表现是否合格的期望结果或判定依据；生成结果应能够对应平台评测数据集的字段结构，例如理想输出评测集所需的参考答案（reference_output）、轨迹评测集所需的执行轨迹信息，涉及工具或技能选择类评估时还应包含可用工具/技能清单（available_tools、available_skills）等字段。

3. **冷启动定位**：生成的用例集合应可作为使用者的首批评测数据集使用——当前平台准备评测数据项主要依赖人工"单个添加/批量导入"或对单条 Trace 手动"加入评测集"，生成能力应能够大幅替代这一人工过程：在使用者尚未准备任何评测数据的前提下，仅依赖已有的 Agent/Skill 代码、执行轨迹与文档，即可获得一份可直接导入平台评测数据集、用于发起评测的数据集。

4. **有效性评分**：应能够自动对生成的用例进行有效性评分，评分应能够反映生成用例标签或期望结果的正确性，并能够在质量存在差异的用例之间体现出区分度；评分结果应能反映用例的可用程度，并帮助使用者识别、区分质量较低或不适合直接使用的用例，评分应支持对单条用例的评估，以及对整体数据集质量的评估；评分逻辑可复用平台已有的评估器体系（如 LLM Judge），也可作为独立的评分结果呈现。

5. **可追溯性**：生成的用例应能够体现其来源依据，使使用者可以判断某条用例是基于哪些输入信息（代码的哪部分、轨迹中的哪个片段、文档中的哪条内容等）生成的。

6. **目标效果**：整体能力应达到降低使用者构建评测数据集门槛、提升评测准备效率的目标，使使用者能够以较低的额外投入获得一份可用的冷启动评测数据集。

### 验收方法

验收应覆盖以下方面，具体验收场景与验收用例由学生自行设计与构造：

1. **输入覆盖能力**：验证在仅提供单一信息源（Agent 代码、Skill 代码、执行轨迹、文档中的任一种）以及提供多种信息源组合的情况下，均能够生成评测用例，且生成结果应能体现出对所提供输入内容的有效利用。

2. **用例可用性**：验证生成的用例是否具备开展一次实际评测所需的完整要素，能够直接或经过必要配置后用于对目标 Agent/Skill 发起一次真实评测，并得到评测结果；其中"直接可用"包括可直接导入或经过少量字段映射后导入平台的评测数据集模块（理想输出评测集/轨迹评测集）。

3. **有效性评分能力**：验证能够对生成的用例给出有效性评分，评分结果应具备可解释性，并能够在质量存在明显差异的用例之间体现出有区分度的评分结果。

4. **冷启动效果**：验证在使用者未提供任何自有评测数据的前提下，生成的用例集合能够独立支撑一次完整的评测流程。

5. **可追溯性**：验证生成的用例能够关联到其所依据的输入信息来源。

验收时应明确说明所依据的具体输入材料（代码、Trace、文档样例等）与验收环境，并针对上述各项要求逐一说明满足情况及依据。

### 完成度标准

对学生的任务完成度按高、中、低三档评估，沿用验收方法中的五个维度，逐项判断达成程度，再综合得出总体档位。

**输入覆盖能力**

- 高：代码、Skill 代码、Trace、文档四类信息源均可独立驱动生成，且支持多源组合生成，组合时能体现出对多来源信息的综合利用，而非简单拼接各来源各自的生成结果。
- 中：支持三类及以上信息源独立生成，但多源组合能力较弱，或某一类信息源的支持不完整。
- 低：仅支持一到两类信息源，且不支持任何形式的多源组合。

**用例可用性**

- 高：生成用例要素完整，与平台评测数据集字段结构兼容或仅需少量映射，可直接或仅需极少配置即可用于对目标 Agent/Skill 发起一次真实评测并得到有效结果，覆盖场景较为多样。
- 中：生成用例要素基本齐全，但需要人工补充或调整才能真正跑通一次评测，或场景覆盖单一、重复度高。
- 低：生成用例要素缺失，无法直接支撑真实评测，或生成结果大量不可用。

**有效性评分能力**

- 高：能对生成的用例自动给出有效性评分，评分结果具备可解释性，且在质量存在明显差异的用例之间能体现出有区分度的分数，支持整体数据集层面的质量评估。
- 中：具备自动评分机制，但可解释性不足，或区分度有限。
- 低：评分机制缺失或形同虚设，如固定分数或评分与用例质量无关。

**冷启动效果**

- 高：在不依赖使用者提供任何自有评测数据的前提下，生成的用例集合能够直接导入平台评测数据集，独立支撑一次完整评测流程并产出评测结果。
- 中：需要使用者补充少量数据或人工介入才能完成一次完整评测。
- 低：生成结果无法独立支撑评测流程，仍需使用者从零构建评测数据。

**可追溯性**

- 高：每条用例均可关联到其所依据的具体输入内容，如代码片段、Trace 片段、文档段落。
- 中：能关联到输入来源的类型或大致范围，但无法定位到具体片段。
- 低：无法说明用例的生成依据。

**综合定档规则**

以"有效性评分能力"与"冷启动效果"两个维度作为核心判定依据，对应任务背景中"自动评分""降低评测门槛、快速启动评测"这两个最核心的诉求，其余维度作为辅助判定：

- 高：核心两个维度均达到高档，其余维度不低于中档。
- 中：核心两个维度均不低于中档，或其中一个维度为高档、另一个不低于中档，其余维度允许存在低档。
- 低：核心两个维度中至少一个为低档，或多数维度整体处于低档。

## 任务二：自演进的 Agent 故障因果归因（Trace 自动化定界定位）

### 任务背景

Agent 尤其是长程任务在执行过程中一旦发生异常，其执行轨迹（Trace）往往包含几十到上百个步骤，涉及多轮工具调用、多角色协作甚至多个 Agent 交叉执行。人工通读原始 Trace 逐步排查故障根因，效率极低，难以满足实际运维和迭代的需求，因此需要具备基于 Trace 自动化定界定位故障根因的能力。

直接依赖大模型对故障 Trace 进行分析存在局限：大模型在处理这类问题时表现出的更多是相关性分析的特征，而非严格的因果推理，容易将"表现相关"误判为"存在因果"。在"一因多果"的场景下——即一个底层根因经过级联传播，在下游产生了多个表现各异的错误现象——这种局限会被进一步放大：模型可能把级联传播产生的多个下游错误分别识别为独立的根因，而非追溯到真正唯一的根本原因，导致归因结果冗余、不准确，甚至误导后续排查方向。更复杂的情况下还可能出现“多因多果”的场景——即多个相互独立的根因同时存在，各自引发一条或多条下游级联错误——这类场景对因果关系的辨析要求更高，系统不仅要分别识别出每一个根因，还要正确区分不同根因各自对应的下游影响范围，避免把不同根因引发的错误相互混淆、张冠李戴。

Agent Insight 目前已经具备一套智能诊断能力：基于 Memory、Reflection、Planning、Action、System 五维认知归因框架，采用预检、检测、归因三阶段分析流程，融合确定性规则与 LLM 语义判别，能够对故障 Trace 给出分钟级的结构化定位结论，并已沉淀了一套覆盖多类典型故障模式的模式库。但其归因路径本质上仍是"预置维度框架 + 模型语义判别"的组合，尚未针对"一因多果""多因多果"这类复杂因果结构系统性地引入严格意义上的因果推理方法，也没有建立起可随案例积累而持续演进的经验闭环——即前文所述的相关性误判风险与经验无法复用的问题，在现有实现中同样存在。

与此同时，故障归因是一项高度依赖经验积累的工作：很多故障具有重复性，专家与新手的差距很大程度上来自"是否踩过同样的坑"。如果每一次归因分析都从零开始，无法把已经经过人工确认的历史分析结果转化为可复用的经验，归因能力就无法随着使用而提升。因此，需要为故障归因引入"自演进"的能力，使系统能够把人工确认过的分析结果沉淀为案例经验，并用这些经验辅助后续同类或相关故障的归因分析，形成越用越准的正向循环。

需要特别说明的是：本课题的目标并非在 Agent Insight 现有智能诊断的五维归因框架内做增量优化或功能扩展，而是要求学生跳出现有实现路径，独立探索并实现一套新的故障因果归因机制，重点解决现有方案尚未系统覆盖的严格因果推理与经验自演进问题。探索过程中可以自由选择具体的技术路线（如结构化因果图、反事实推理、约束满足式排查等），不要求复用现有的五维认知归因框架、故障模式库或诊断界面，也不强制要求与现有智能诊断模块打通集成；新机制未来是否反哺、替代或与现有智能诊断整合，由后续迭代决定，不作为本课题的验收要求。

### 任务描述

需要实现面向 Agent 故障的自动化因果归因能力，本课题作为独立于 Agent Insight 现有智能诊断模块的新机制进行探索，不要求复用或替换现有的五维认知归因实现；但新机制仍需要以功能模块形式集成到 Agent Insight 平台中（如新增独立入口/页面，或提供可被平台其他模块调用的服务接口），使其成为平台内可交付、可运行的能力，而不是脱离平台的独立研究原型，具体需求如下：

1. **定界定位**：针对一次故障的 Agent 执行轨迹（Trace），应能自动分析并定位导致故障的具体环节，包括但不限于涉及的 Agent、执行步骤或组件，定位结果应具备可追溯的依据，能够说明得出该结论所依据的 Trace 内容。

2. **因果而非相关性识别**：应能够处理"一个根因级联传播、产生多个下游错误表现"（一因多果）以及"多个根因同时存在、各自引发下游级联错误"（多因多果）等场景，准确识别出真正的根本原因及其对应的下游影响范围，而不是将级联传播产生的下游错误笼统地作为并列根因输出，也不应将不同根因各自引发的下游错误相互混淆。

3. **人工确认机制**：应支持人工对归因分析结果进行确认或纠正，确认或纠正后的结果应能够被系统识别和记录，作为后续经验沉淀的输入来源。

4. **经验沉淀与复用（自演进）**：应支持将经过人工确认的分析结果沉淀为可复用的案例经验，沉淀的经验应能够在后续同类或相关故障的归因分析中被实际调用并发挥辅助作用，具体的沉淀形式（如用于模型微调的数据、用于分析时参考的上下文/知识库等）不做限定，由具体方案决定。

5. **持续演进效果**：整体能力应随着案例经验的积累呈现出可衡量的提升趋势，即归因的准确性、效率或所需人工介入程度应随着系统使用（案例积累）而变好，而非一成不变。

6. **经验沉淀的稳健性**：经验沉淀与复用机制应具备一定的稳健性保障，避免因个别历史案例的误判、或从局部案例中不恰当泛化出的规律，被不加区分地应用到新的故障场景中，从而对新场景的归因结果产生负面影响。

### 验收方法

验收数据集以 Who&When（ICML 2025 Spotlight 提出的多智能体失败归因基准）与 AgentChaosBench（基于故障注入构建的运行时故障检测与定位基准）为主，两者均提供已知根因标注（ground truth），除"多因多果"场景外，其余场景（单一根因导致单一错误表现、"一因多果"即根因级联传播产生多个下游错误表现等）均直接基于这两个数据集进行验证。目前业界公开数据集中较少覆盖"多因多果"（多个独立根因同时存在、各自引发下游级联错误）场景，这部分需要在上述数据集基础上自行构造，例如将多条独立的单根因案例按一定方式组合、交织，人为构造出同一次执行中存在多个独立根因的复合场景。学生可自行决定将 Who&When 与 AgentChaosBench 中的哪些 case 用于"自演进效果"的验证，即哪些用于系统学习、沉淀经验，哪些用于对比验证，具体验收场景与验收用例由学生自行设计与构造，验收应覆盖以下方面：

1. **定界定位能力**：验证针对给定的故障 Trace，系统能够输出具体的定位结果，且定位结果能够说明其依据、可被追溯核实；验证场景应覆盖不同复杂度的因果结构，包括单一根因导致单一错误表现、"一因多果"（单一根因级联产生多个下游错误表现）、"多因多果"（多个根因同时存在、各自引发下游级联错误）等情况，系统应能在这些场景下准确区分根因与下游表现，正确关联根因与其对应的下游影响范围，而不是把级联表现误判为并列根因，或把不同根因引发的下游错误相互混淆。

2. **人工确认与经验沉淀流程**：验证人工对分析结果进行确认或纠正的流程是否可行，验证被确认或纠正的结果能否被实际沉淀为经验，而非仅停留在记录层面。

3. **自演进效果**：验证系统在积累一定数量经人工确认的历史案例后，相较于未积累经验的初始状态，对同类或相关故障的归因效果（如准确率、效率或所需人工介入程度）是否有可衡量的提升，并需说明用于对比的前后条件设置。

4. **稳健性**：验证在引入经验沉淀与复用机制后，系统对与历史案例不完全相同或不适用历史经验的新故障场景，其归因结果不会因不当套用历史经验而出现明显劣化。

5. **分析结果一致性**：验证对同一条故障 Trace 进行多次独立分析，各次分析得出的定位结果应保持一致，不应出现同一输入在不同次分析中得出不同结论的情况。

验收时应明确说明所依据的具体输入材料（故障 Trace 样例、人工确认记录等）与验收环境，并针对上述各项要求逐一说明满足情况及依据。

### 完成度标准

对学生的任务完成度按高、中、低三档评估，沿用验收方法中的四个维度，逐项判断达成程度，再综合得出总体档位。

**定界定位能力**

- 高：对单一根因单一表现、一因多果、多因多果等不同复杂度的因果场景均能给出准确的定位结果，定位结果可追溯、依据清晰；面对多因多果场景能正确区分不同根因各自对应的下游影响范围，不发生根因与下游表现混淆或张冠李戴。
- 中：对单一根因场景和一因多果场景能给出基本准确的定位结果，但在多因多果等更复杂场景下存在明显的混淆或误判。
- 低：仅能处理单一根因单一表现的简单场景，无法正确处理级联传播导致的多个下游表现，或定位结果缺乏可追溯依据。

**自演进效果**

- 高：在积累一定数量经人工确认的历史案例后，对同类或相关故障的归因效果（准确率、效率或所需人工介入程度）有明确可衡量的提升，且提升趋势可复现。
- 中：能观察到一定的提升趋势，但幅度有限，或提升效果不稳定、难以复现。
- 低：积累经验前后归因效果无明显差异，自演进机制未实质性发挥作用。

**稳健性**

- 高：面对与历史案例不完全相同或不适用历史经验的新故障场景，归因结果保持稳定，未因不当套用历史经验出现明显劣化。
- 中：多数情况下能保持稳定，但在个别场景下存在因套用历史经验导致的误判。
- 低：经验沉淀机制存在明显的过拟合或误泛化问题，新场景归因效果因套用不适用的历史经验而明显劣化。

**分析结果一致性**

- 高：对同一条故障 Trace 反复多次独立分析，定位结果（涉及的根因、影响范围等）保持完全一致，不存在因随机性导致结论漂移的情况。
- 中：多数情况下结果一致，但存在少量因随机性导致的结论漂移，且漂移幅度较小，核心结论不变。
- 低：同一输入多次分析结果不稳定，核心结论（如判定的根因）在不同次分析中出现明显差异。

**综合定档规则**

以"自演进效果"与"稳健性"两个维度作为核心判定依据，对应"自演进"这一任务的核心诉求——既要真正越用越准，又不能学偏，其余两个维度作为辅助判定：

- 高：核心两个维度均达到高档，其余维度不低于中档。
- 中：核心两个维度均不低于中档，或其中一个维度为高档、另一个不低于中档，其余维度允许存在低档。
- 低：核心两个维度中至少一个为低档，或多数维度整体处于低档。

## 任务三：问答小助手（知识库问答插件）

### 任务背景

很多网站、产品或团队都积累了大量文档资料（如产品手册、常见问题、内部规范等），用户或访客常常需要从这些资料中查找答案，但直接翻阅大量文档效率低、体验差。同时，直接依赖大模型回答用户问题存在捏造事实（hallucination）的风险——当问题超出已有知识范围时，大模型可能给出看似合理但实际错误的答案，这在面向真实用户的场景下是不可接受的。

因此，需要构建一个基于知识库的问答小助手：一方面要能够方便地把分散在不同来源、不同格式的文档转化为可供检索问答的知识库，并支持对知识库内容的持续维护；另一方面，问答能力需要具备"有据可依"的特性——回答必须基于知识库内容、给出可核实的引用来源，遇到知识库未覆盖的问题时应如实告知用户而不是编造答案。此外，为了让这样的能力能够方便地被各类网站或产品复用，问答助手需要以可嵌入的插件形式提供，而不是绑定在某一个特定系统上。

### 任务描述

需要实现一个基于知识库的问答小助手，并将其作为插件实际集成到 Agent Insight 开源项目中（验证方式见下节第 8 项），具体需求如下：

1. **知识库创建**：应提供 CLI 和网页两种方式创建知识库，支持将问答助手本地目录下的文档、或通过网页上传的指定目录下全部或部分文档导入知识库，文档格式应支持 md、txt、word、excel、pdf 等常见格式。

2. **知识库管理**：应提供知识库管理功能，支持对知识库内容进行新增、删除、修改、查询。

3. **知识库同步更新**：应支持知识库内容的增量更新，当已导入的源文档发生变化时，知识库应能够相应更新，而不需要每次变更都重新全量导入；应支持以问答对形式直接录入知识库内容，而不仅限于导入文档。

4. **插件形态与多轮问答**：问答助手应以可嵌入的网页"插件"形式存在，能够方便地被任意网站集成；集成后应以图标形式悬浮于网站页面之上，点击图标弹出对话框供用户提问；应支持多轮问答，即能够结合上下文进行连续对话。

5. **回答准确性与引用溯源**：问答助手应基于知识库内容准确回答用户问题，回答内容需给出引用来源，用户点击引用来源应能够查看引用内容的详细信息；对于知识库未覆盖或无法准确回答的问题，应以友好的方式告知用户暂时无法回答，不得捏造事实或给出无依据的回答。

6. **检索质量与交互体验**：应具备提升检索准确性的机制（如关键词检索与语义检索相结合等方式），以提高回答内容与用户问题的相关性；应支持以流式方式输出回答内容。

7. **反馈与持续优化**：应支持用户对回答内容进行反馈（如认可或不认可）；对于被反馈为不认可、或问答助手无法准确回答的问题，应能够被记录下来，便于后续针对性地补充和完善知识库内容。

### 验收方法

验收应覆盖以下方面，具体验收场景与验收用例由学生自行设计与构造：

1. **知识库创建能力**：验证能否分别通过 CLI 和网页两种方式，使用本地目录文档以及网页上传目录中的全部或部分文档创建知识库，且能够正确处理 md、txt、word、excel、pdf 等不同格式的文档。

2. **知识库管理能力**：验证知识库内容的新增、删除、修改、查询功能是否可用，操作结果应能够正确反映到知识库中。

3. **知识库同步更新能力**：验证当已导入的源文档发生变化后，知识库内容能否相应更新；验证是否支持以问答对形式直接录入知识库内容。

4. **插件集成与多轮问答**：验证问答助手能否以插件形式集成到任意网站中，集成后能否以图标形式正常展示、点击后能否正常弹出对话框；验证多轮对话场景下，问答助手能否正确理解和使用上下文信息。

5. **回答准确性与引用溯源**：验证问答助手基于知识库内容作答的准确性；验证回答是否给出引用来源，引用来源能否被查看到详细内容；验证对于知识库未覆盖或无法准确回答的问题，问答助手能否以友好方式告知用户，而不产生捏造内容。

6. **检索质量与交互体验**：验证问答助手在提升检索准确性方面所采取的机制是否有效；验证回答内容是否支持流式输出。

7. **反馈与持续优化**：验证用户反馈机制是否可用；验证被反馈为不认可或无法准确回答的问题能否被记录，并能够用于后续知识库内容的补充和完善。

8. **在 Agent Insight 中的集成验证**：验证问答小助手能否作为插件实际集成到 Agent Insight 开源项目中，集成后能否正常展示、正常响应用户提问，验证其在真实项目环境中的可用性。

验收时应明确说明所依据的知识库内容、测试文档与验收环境，并针对上述各项要求逐一说明满足情况及依据。

### 完成度标准

对学生的任务完成度按高、中、低三档评估，沿用验收方法中的八个维度，逐项判断达成程度，再综合得出总体档位。

**知识库创建能力**

- 高：CLI 和网页两种方式均可用，能够正确处理本地目录与网页上传目录中全部或部分文档的选择性导入，md、txt、word、excel、pdf 等格式均能正确解析并进入知识库。
- 中：CLI 和网页两种方式基本可用，但对部分文档格式的解析存在问题，或"部分文档导入"这类选择性场景支持不完整。
- 低：仅支持其中一种创建方式，或多数文档格式无法正确解析导入。

**知识库管理能力**

- 高：知识库内容的增删改查功能完整可用，操作结果准确、及时反映到知识库中，且不影响其他内容的完整性。
- 中：增删改查功能基本可用，但存在个别操作结果不准确或有延迟的情况。
- 低：增删改查功能不完整，或操作后知识库内容出现错误、丢失等问题。

**知识库同步更新能力**

- 高：源文档变化后知识库能够准确、及时同步更新，同时支持以问答对形式直接录入知识库内容。
- 中：具备增量同步能力，但存在同步不及时或不完整的情况；问答对录入功能基本可用但存在局限。
- 低：不具备实质性的增量同步能力，源文档变化后仍需全量重新导入才能生效，或不支持问答对直接录入。

**插件集成与多轮问答**

- 高：能够以插件形式便捷集成到任意网站中，图标展示与对话框交互正常；多轮对话中能够准确理解和运用上下文信息，问答连贯自然。
- 中：插件集成基本可用，但集成过程繁琐或对网站有一定限制；多轮对话能够维持上下文，但存在理解偏差或遗忘的情况。
- 低：插件难以方便地集成到不同网站中，或多轮对话无法有效利用上下文，退化为单轮问答。

**回答准确性与引用溯源**

- 高：回答内容准确、紧扣知识库内容，均能给出可核实的引用来源，且引用详情可正常查看；对知识库未覆盖或无法准确回答的问题，能够以友好方式如实告知，未出现捏造事实的情况。
- 中：多数情况下回答准确并能给出引用，但存在个别引用不准确、引用详情查看不完整，或在少数情况下出现无依据回答的情况。
- 低：回答准确性差，缺少引用来源或引用与回答内容不对应，或存在明显的捏造事实、无依据作答的情况。

**检索质量与交互体验**

- 高：检索机制能够有效提升回答与用户问题的相关性，在语义相近但表述不同的提问下仍能准确检索到相关内容；回答内容能够以流式方式输出，交互流畅。
- 中：检索机制在常规提问下表现尚可，但对表述差异较大的问题检索效果明显下降；流式输出基本可用但存在明显卡顿或不完整的情况。
- 低：检索机制效果差，常规提问也难以检索到相关内容；不支持流式输出，或输出体验差。

**反馈与持续优化**

- 高：用户反馈机制完整可用；被反馈为不认可或无法准确回答的问题能够被准确记录，且记录内容可用于后续知识库内容的补充和完善。
- 中：反馈机制基本可用，但记录的问题信息不完整，或记录内容难以直接用于知识库补充。
- 低：不具备实质性的反馈或问题记录能力，用户反馈无法被有效收集和利用。

**在 Agent Insight 中的集成验证**

- 高：能够将问答小助手完整集成到 Agent Insight 开源项目中，集成过程顺畅，集成后在真实项目环境中展示与问答功能均正常，与其他既有功能无明显冲突。
- 中：能够完成集成，但过程中存在需要额外调整或存在局限的情况，或集成后部分功能在真实项目环境中表现不如独立环境稳定。
- 低：无法在 Agent Insight 开源项目中完成实际集成，或集成后问答小助手无法正常展示或响应。

**综合定档规则**

以"回答准确性与引用溯源"与"插件集成与多轮问答"两个维度作为核心判定依据，对应问答小助手最核心的诉求——既要能被方便地嵌入任意网站正常使用，又要保证回答有据可依、不捏造事实，其余维度作为辅助判定：

- 高：核心两个维度均达到高档，其余维度不低于中档。
- 中：核心两个维度均不低于中档，或其中一个维度为高档、另一个不低于中档，其余维度允许存在低档。
- 低：核心两个维度中至少一个为低档，或多数维度整体处于低档。

## 任务四：多 Trace 故障关联分析（故障传播桑基图生成）

### 任务背景

当前 Agent Insight 的智能诊断能力聚焦于单条 Trace 的根因定位，解决的是"这一次故障是怎么发生的"这个问题。但在实际运维和迭代场景中，单次故障往往不是孤立事件——很多故障具有重复性、模式化的特征，同一个底层缺陷可能在不同时间、不同任务中反复触发，只是每次的直接表现（下游错误现象）不完全一样。如果只停留在逐条分析单个 Trace，就无法回答"这类故障到底有多常见""最常见的故障传播路径是什么""哪些环节是故障传播的关键枢纽"这类更宏观的问题，而这些问题对于问题优先级排序、系统性修复往往更有价值。

因此，需要在单条 Trace 归因能力的基础上，进一步支持跨多条 Trace 的故障关联分析——识别不同 Trace 中故障根因与传播路径的共性和差异，并以直观的方式呈现给使用者，帮助其发现系统性、模式化的问题，而不仅仅是逐个击破孤立事件。桑基图这种可视化形式天然适合表达"从多个来源节点流向多个去向节点、且流量大小不同"的关系，用它来呈现"故障从触发点到下游影响的传播路径及其在多次故障中的出现频次或强度"，能够让使用者一眼看出最主要的故障传播模式和影响范围，是这类分析结果的合适呈现方式。

### 任务描述

需要实现基于多条 Agent 执行 Trace 的故障关联分析与可视化能力，该能力需要集成到 Agent Insight 平台中，使平台用户可以直接在 Agent Insight 中查看多 Trace 关联分析结果与故障传播桑基图，具体需求如下：

1. **多 Trace 输入与关联分析**：应支持对一批（多条）Agent 执行 Trace 进行分析，识别不同 Trace 之间在故障根因、故障传播路径上的关联性，而不仅限于对单条 Trace 的独立分析。

2. **故障传播路径识别**：应能够识别故障从触发点（根因）到下游各级受影响环节的传播路径，当同一故障传播路径在不同 Trace 中重复出现时，应能够将其识别为同一类传播模式，而不是每次都作为独立结果输出。

3. **桑基图生成**：应能够基于多 Trace 的故障关联分析结果生成故障传播桑基图，桑基图应能够体现故障从根因到下游各级影响环节的传播路径，以及每条传播路径在所分析的多条 Trace 中出现的相对频次或强度。

4. **可交互与可追溯**：桑基图中的节点与连接应能够关联回其所依据的具体 Trace 及原始故障归因结果，使使用者可以从桑基图定位到具体的 Trace 与归因依据进行核实。

5. **规模适应性**：分析与桑基图生成能力应能够适应所分析 Trace 数量和故障传播路径复杂度的变化，即分析结果的可靠性与呈现的可读性不应随着输入 Trace 数量的增加或故障传播路径的增多而明显下降。

6. **与既有能力的衔接**：应能够利用已有的单 Trace 故障归因能力或其归因结果，作为多 Trace 关联分析的输入基础，而不是重新独立实现一套单 Trace 分析能力。

### 验收方法

验收应覆盖以下方面，具体验收场景与验收用例由学生自行设计与构造：

1. **多 Trace 关联分析能力**：验证针对给定的一批故障 Trace，系统能否识别出其中在故障根因、传播路径上存在关联的 Trace，而不是将每条 Trace 完全独立处理。

2. **传播路径归并能力**：验证同一故障传播路径在多条 Trace 中重复出现时，系统能否将其识别、归并为同一类传播模式，而不是重复输出为多个独立结果。

3. **桑基图生成能力**：验证系统能否基于分析结果生成故障传播桑基图，桑基图应能体现从根因到下游各级影响环节的传播路径，以及各传播路径在所分析 Trace 中的相对频次或强度。

4. **可交互与可追溯性**：验证桑基图中的节点或连接是否可关联回具体的 Trace 与归因依据，验证使用者能否据此定位并核实原始信息。

5. **规模适应性**：验证分析结果的可靠性与桑基图的可读性，在所分析 Trace 数量或故障传播路径复杂度增加时是否保持在可接受水平。

6. **与既有能力的衔接**：验证多 Trace 关联分析是否能够利用已有的单 Trace 故障归因能力或其归因结果作为输入。

验收时应明确说明所依据的具体输入材料（多条故障 Trace 样例等）与验收环境，并针对上述各项要求逐一说明满足情况及依据。

### 完成度标准

对学生的任务完成度按高、中、低三档评估，沿用验收方法中的六个维度，逐项判断达成程度，再综合得出总体档位。

**多 Trace 关联分析能力**

- 高：能够准确识别一批 Trace 中在故障根因、传播路径上存在关联的 Trace，关联判断依据清晰、可追溯，不会将明显相关的 Trace 遗漏或将不相关的 Trace 误判为关联。
- 中：能够识别出部分关联，但存在一定的遗漏或误判，关联判断依据不够清晰。
- 低：无法有效识别 Trace 之间的关联，基本等同于对每条 Trace 独立处理。

**传播路径归并能力**

- 高：同一故障传播路径在不同 Trace 中重复出现时，能够准确识别并归并为同一类传播模式，归并结果不出现明显的重复或错误拆分。
- 中：具备归并能力，但存在部分重复模式未被正确归并，或不同模式被错误合并的情况。
- 低：不具备实质性的归并能力，同一传播模式在不同 Trace 中被反复作为独立结果输出。

**桑基图生成能力**

- 高：桑基图能够准确、清晰地体现从根因到下游各级影响环节的传播路径，各路径宽度能够真实反映其在多条 Trace 中的相对频次或强度，图形可读性好。
- 中：桑基图基本能够体现传播路径及相对强度，但在路径较多或结构复杂时可读性下降，或频次、强度的呈现不够准确。
- 低：桑基图无法准确体现传播路径或相对强度，或生成的图形难以辨认、误导使用者判断。

**可交互与可追溯性**

- 高：桑基图中的节点与连接均可关联回具体的 Trace 与归因依据，使用者可以顺畅地定位并核实原始信息。
- 中：部分节点或连接可关联回原始信息，但关联不完整或操作不够顺畅。
- 低：桑基图节点与连接无法关联回具体 Trace 或归因依据，结果不可核实。

**规模适应性**

- 高：随着分析的 Trace 数量或故障传播路径复杂度增加，分析结果的可靠性和桑基图的可读性均保持在可接受水平。
- 中：在 Trace 数量或复杂度明显增加时，分析结果可靠性或图形可读性出现一定程度的下降，但基本可用。
- 低：Trace 数量或复杂度增加后，分析结果明显不可靠，或桑基图难以正常呈现和使用。

**与既有能力的衔接**

- 高：多 Trace 关联分析能够充分利用已有的单 Trace 故障归因能力或其归因结果作为输入，未重复实现单 Trace 分析能力。
- 中：部分利用了已有能力，但存在重复实现或衔接不顺畅的情况。
- 低：完全独立于已有的单 Trace 归因能力重新实现，未形成能力复用。

**综合定档规则**

以"多 Trace 关联分析能力"与"传播路径归并能力"两个维度作为核心判定依据，对应这个任务相较于单条 Trace 归因真正新增的核心价值——能否准确识别并归并跨 Trace 的关联与共性传播模式，其余维度作为辅助判定：

- 高：核心两个维度均达到高档，其余维度不低于中档。
- 中：核心两个维度均不低于中档，或其中一个维度为高档、另一个不低于中档，其余维度允许存在低档。
- 低：核心两个维度中至少一个为低档，或多数维度整体处于低档。

## 任务五：Agent 经验库（Trace 经验挖掘与 Skill 化召回）

### 任务背景

Agent Insight 目前已适配 OpenCode、Claude Code、Hermes、Trae IDE、JiuwenSwarm 等 10+ 主流 Agent 平台，持续采集这些第三方 Agent 的完整执行轨迹（Trace）。但这些 Trace 目前主要用于链路追踪、评测与故障诊断（见任务二），其中大量反复出现的有效执行流程、正确的工具调用参数构造方式、常见错误的修复方法等信息尚未被系统性挖掘、复用——同类任务在不同 Agent、不同时间执行时，仍然需要各自"从零试错"，任务的执行成功率与稳定性并不会随着 Agent Insight 采集数据的增多而自然提升。

阿里云 AgentLoop 已经提出并落地了"经验库"能力可供参考。其核心定位是：知识库帮助 Agent"知道什么"，经验库帮助 Agent 判断"在当前情境下应该怎么做"——经验库保存的不是某一次任务的具体答案，而是能够支撑下一次任务的方法。具体机制上，AgentLoop 从真实执行轨迹中做步骤级（而非整条会话级）的证据挖掘：识别单次工具调用中参数的来源与构造方式（如某个文件路径是来自用户任务描述、还是来自前一步工具返回并验证过的结果），将不同 Agent 框架中语义相同的操作统一映射为标准化的能力标识，再以这一规范化结构为依据对来自不同 Trace、不同任务表述的证据做哈希聚类，把"底层做法相同但表面问题不同"的多条 Trace 归并为同一条可复用经验，并统计每条经验的支持、成功、失败与反例数量作为质量依据。经验的实际使用也有明确设计：召回能力被封装为一个可安装到目标 Agent（如 OpenCode）中的 Skill，由该 Skill 自行判断当前任务是否命中已有经验、什么时候应该触发召回。

但这套机制也暴露出可解释性上的缺口：经验的成败判定目前只保留汇总统计量，没有留存"具体是哪条 Trace 的哪一次工具调用被判定为支持还是反例"这一级别的证据与理由，这导致当同一条 Trace 中出现与当前经验规则无关的后续错误时，可能被错误地归因到实际执行成功的某个规则上；同时，经验对外展示的标题、摘要有时会借用某一具体代表性案例命名（如以"Kerberos"命名一条实际适用于任意日志文件读取场景的通用参数规则），容易让使用者误判该经验真实的适用边界。

因此，Agent Insight 需要面向已接入平台的第三方 Agent，构建一套服务于这些 Agent 自身执行能力的经验库：从它们已采集的历史 Trace 中挖掘可复用经验，并以 Skill 形式集成回这些 Agent，使其在执行同类或相关任务时能够召回并实际应用这些经验；同时在证据留存与经验适用边界的呈现上，弥补业界现有方案暴露出的可解释性缺口。该能力服务对象是接入平台的第三方 Agent 本身，不用于 Agent Insight 平台自身的诊断、评测生成等内部能力（相关能力已在任务二中单独覆盖）。

### 任务描述

需要实现面向第三方 Agent 的经验库能力：经验的挖掘、聚类、质量评估与沉淀需要集成到 Agent Insight 平台中（作为面向已接入 Agent 的新功能模块，由平台基于已采集的历史 Trace 完成），召回与实际应用则以 Skill 形式安装到目标第三方 Agent 框架中，具体需求如下：

1. **经验挖掘的输入与粒度**：应基于接入平台的第三方 Agent 产生的历史执行轨迹（Trace）自动挖掘经验，挖掘粒度应精确到步骤级（如单次工具调用），不能仅对整条 Trace 或整次任务做粗粒度总结；应能够识别 Trace 中反复出现的有效执行做法，也应能够识别高风险、易出错的路径并从中提炼修复或规避方法。

2. **经验类型覆盖**：应支持挖掘多种类型的经验，覆盖但不限于任务执行的流程步骤序列、工具调用的正确参数构造与验证方式、常见错误的修复方法这三类，不应仅支持单一笼统类型的"经验"。

3. **跨 Agent 框架的工具标准化**：面对不同第三方 Agent 框架产生的 Trace，应能够将其中语义相同但命名、调用形式不同的工具或操作，统一映射为标准化的能力标识，使源自不同 Agent 框架的 Trace 可以基于统一维度进行比较和聚合，而不是只能在单一框架内部聚合经验。

4. **跨 Trace 聚类与参数血缘**：应能够识别不同 Trace 之间任务表述不同、但底层执行步骤结构相同的情况，将其归并为同一条可复用经验，而不是因为表面问题不同就将本质相同的做法当作互不相关的独立经验重复保留；对于涉及具体参数的经验，应能够追踪关键参数值的来源（如来自用户任务描述、来自前序工具调用的返回结果，或为凭空构造/模型臆测），并标注该来源是否经过验证。

5. **Skill 化的经验召回与集成**：经验的召回与使用应以 Skill 的形式提供，即开发可安装到第三方 Agent 框架（如 OpenCode、Claude Code 等）中的经验召回 Skill，由该 Skill 自行判断当前任务是否命中已有经验、何时应当触发召回，并在触发后将召回到的相关经验实际用于指导当前任务的执行。

6. **证据可追溯与失败归因准确性**：每条经验的沉淀应基于对每一条支持/反驳证据的独立判定，能够追溯到具体是哪条 Trace 的哪一次工具调用被判定为支持还是反例，以及判定的具体理由；应避免将某条 Trace 中与当前经验规则无关的后续步骤失败，错误归因为该经验规则本身无效。

7. **经验质量与适用边界呈现**：应对沉淀的经验进行质量评估，评估结果应能够区分证据支持充分、可信度较高的经验与证据不足、存在争议的经验；经验对使用者呈现的标题、摘要等描述，应准确反映其底层规则的真实适用范围，不应因挖掘时选取了某个具体代表性案例，而使标题、摘要的字面含义明显窄于该经验实际可适用的场景范围。

8. **召回实际效果**：应能够验证被召回的经验确实被目标 Agent 实际用于指导任务执行，并对同类或相关任务的执行效果（如任务成功率、重复试错次数、执行稳定性等）产生可衡量的正向影响。

### 验收方法

验收应覆盖以下方面，具体验收场景与验收用例由学生自行设计与构造：

1. **经验挖掘能力**：验证系统能否基于给定的第三方 Agent 历史 Trace，在步骤级粒度上挖掘出经验，验证挖掘结果既能覆盖反复出现的有效做法，也能覆盖对高风险/易出错路径提炼出的修复方法。

2. **经验类型覆盖**：验证系统能否分别挖掘出流程步骤序列、工具调用参数构造与验证方式、常见错误修复方法这三类经验，而不是只能生成单一类型的经验。

3. **跨框架工具标准化**：验证在提供来自两种及以上不同 Agent 框架的 Trace 时，系统能否将其中语义相同的工具/操作正确映射为统一的能力标识，并验证基于该标识能否实现跨框架的经验聚合。

4. **跨 Trace 聚类与参数血缘**：验证给定多条任务表述不同、但底层执行步骤结构相同的 Trace 时，系统能否将其正确聚合为同一条经验，而不是拆分为多条重复经验；验证参数类经验中，参数值的来源判定与验证状态标注是否准确。

5. **Skill 化召回验证**：验证经验召回能力是否以 Skill 形式提供，能否被实际安装到至少一种第三方 Agent 框架中；验证该 Skill 能否根据当前任务自行判断是否命中已有经验、是否触发召回。

6. **证据可追溯与失败归因准确性**：验证每条经验能否追溯到具体的支持/反例证据（哪条 Trace 的哪次工具调用），以及对应的判定理由；构造包含"该 Trace 后续存在与当前经验规则无关的失败步骤"这一场景，验证系统是否会将该失败错误地归因到实际执行成功的经验规则上。

7. **质量与适用边界呈现**：验证系统能否对经验给出质量评估，并在证据支持充分与证据不足的经验之间体现出区分度；验证在挖掘时使用了具有代表性但表述较窄的案例（如以某个具体业务场景命名）的情况下，生成的经验标题、摘要是否仍能准确反映其底层规则的实际适用范围，而不会明显窄于真实适用场景。

8. **召回实际效果**：验证被召回的经验能否被目标 Agent 实际用于指导任务执行；对同类或相关任务，验证引入经验召回前后，任务执行效果（成功率、重复试错次数、执行稳定性等中的至少一项）是否有可衡量的正向变化。

验收时应明确说明所依据的具体输入材料（第三方 Agent 历史 Trace 样例、目标 Agent 框架、召回前后对比设置等）与验收环境，并针对上述各项要求逐一说明满足情况及依据。

### 完成度标准

对学生的任务完成度按高、中、低三档评估，沿用验收方法中的八个维度，逐项判断达成程度，再综合得出总体档位。

**经验挖掘能力**

- 高：能够稳定实现步骤级粒度的经验挖掘，既能识别反复出现的有效做法，也能从高风险/易出错路径中提炼出有效的修复或规避方法。
- 中：能够实现步骤级挖掘，但对高风险路径的识别与修复方法提炼能力较弱，或挖掘结果稳定性一般。
- 低：仅能对整条 Trace 做粗粒度总结，无法精确到步骤级，或挖掘结果大量不可用。

**经验类型覆盖**

- 高：能够稳定挖掘出流程步骤序列、参数构造与验证方式、错误修复方法三类经验。
- 中：能够挖掘出其中两类经验，第三类支持不完整或效果较差。
- 低：仅能挖掘出单一类型的经验。

**跨框架工具标准化**

- 高：能够将不同 Agent 框架中语义相同的工具/操作准确映射为统一能力标识，基于该标识可以实现稳定的跨框架经验聚合。
- 中：具备标准化映射能力，但对部分工具的映射不准确，或跨框架聚合存在明显遗漏。
- 低：不具备跨框架标准化能力，经验挖掘与聚合只能在单一 Agent 框架内部进行。

**跨 Trace 聚类与参数血缘**

- 高：能够准确识别底层步骤结构相同但表面任务表述不同的 Trace，将其正确聚合为同一条经验；参数来源判定与验证状态标注准确。
- 中：聚类能力基本可用，但存在部分应合并的 Trace 未被合并，或参数血缘判定存在个别错误。
- 低：不具备实质性的跨 Trace 聚类能力，表面问题不同的 Trace 即便底层做法相同也被当作独立经验重复保留，或参数血缘信息缺失。

**Skill 化召回验证**

- 高：经验召回以 Skill 形式提供，能够被实际安装到第三方 Agent 框架中并正常运作，Skill 能够自行准确判断何时触发召回。
- 中：具备 Skill 化召回能力，但安装或触发判断存在一定局限，或仍依赖少量额外配置/接口辅助。
- 低：未以 Skill 形式提供召回能力，或 Skill 无法在目标 Agent 框架中正常运作，触发判断机制形同虚设。

**证据可追溯与失败归因准确性**

- 高：每条经验均可追溯到具体的支持/反例证据及判定理由；在存在无关失败步骤的场景下，系统不会将其错误归因到实际执行成功的经验规则上。
- 中：多数经验可追溯到证据来源，但存在个别经验的判定理由不清晰，或在少数场景下出现归因不准确的情况。
- 低：经验的成败判定仅有汇总统计，无法追溯到具体证据，或普遍存在将无关失败错误归因到有效规则上的问题。

**质量与适用边界呈现**

- 高：能够对经验给出有区分度的质量评估；经验标题、摘要能够准确反映底层规则的真实适用范围，不会因代表性案例的选取而产生误导。
- 中：质量评估基本可用但区分度有限；标题、摘要多数情况下能准确反映适用范围，但存在个别以偏概全的情况。
- 低：不具备实质性的质量评估机制；标题、摘要经常明显窄于或不符合经验实际的适用范围，容易误导使用者。

**召回实际效果**

- 高：被召回的经验能够被目标 Agent 实际用于指导任务执行，且对同类或相关任务的执行效果（成功率、重复试错次数、执行稳定性等）产生明确、可复现的正向影响。
- 中：召回结果能被实际使用，但对执行效果的提升有限，或提升效果不够稳定。
- 低：召回的经验未被实际用于指导任务执行，或引入经验召回前后任务执行效果无明显差异。

**综合定档规则**

以"召回实际效果"与"证据可追溯与失败归因准确性"两个维度作为核心判定依据：前者对应经验库最终能否真正让接入的第三方 Agent 变得更好用这一核心目标，后者对应业界现有方案已经暴露出的可解释性缺口——避免把与经验规则无关的失败错误归因到有效规则上，是经验库能够被使用者信任、长期可靠使用的前提，其余维度作为辅助判定：

- 高：核心两个维度均达到高档，其余维度不低于中档。
- 中：核心两个维度均不低于中档，或其中一个维度为高档、另一个不低于中档，其余维度允许存在低档。
- 低：核心两个维度中至少一个为低档，或多数维度整体处于低档。

## 任务六：Agent 评测小模型

### 任务背景

Agent Insight 当前的评测能力（详见 `src/lib/evaluators/` 预置评估器目录与《质量监控 — 全量自动评测与可信度体系》设计规格）本质上都是 **LLM-as-a-Judge（LLMAJ）**：无论是"Agent 任务完成度""Agent 轨迹质量"这类聚合型评估器，还是"结果准确性""答案质量""指令遵循"这类结果维评估器，运行方式都是 `direct-llm`（异步调用大模型做多 token 生成式打分）或 `agent`（起一次 opencode 会话）。质量监控设计规格里也明确写到"本期成本约束：暂不做成本治理，默认所有需要模型的评估一律走异步模型调用（预算/采样/限流留作后续）"——也就是说，随着 trace 上报量增长，全量评测的成本、延迟压力会持续放大，而 LLM Judge 依赖开放式生成，措辞、解码的微小变化也会带来评分的非确定性，这与"每条 trace 都要评、且要能作为线上护栏使用"的目标存在结构性矛盾。该设计规格已经在参考 Galileo 的 reference-free Correctness / Instruction Adherence 概念来设计无标准答案评测，但尚未涉及"如何用更低成本、确定性的方式跑这些判定"这一层。

Galileo Luna-2（Goel et al., 2026，arXiv:2602.18583）针对的正是这个问题：把 decoder-only 小语言模型（SLM）改造成"单 token 确定性分类器"——每个指标对应一个共享同一基座骨干的轻量适配器（LoRA，参数量约为基座的 3%），推理时只看类别 token（如 true/false）的归一化概率作为判定与置信度，不做多 token 生成，因此天然确定性、且多个指标可在同一次前向中并发复用 backbone 激活、只切换适配器。论文报告其在多个指标上的 F1 已与"GPT-4.1 + ChainPoll（重复 3 次取平均）"基本持平，而成本降低约 80 倍、延迟降低约 20 倍。

本任务要求参考 Luna-2 的技术方案，实现一个用于 Agent 评测的小模型（并非要求照搬其模型权重或代码），验证"共享小模型骨干 + 单 token/确定性分类范式"是否能在准确率基本不降的前提下大幅降低成本与延迟。为控制任务规模，**验证范围收敛到以下六个指标，不要求覆盖 Luna-2 官方支持的全部 20+ 指标**（安全合规类如 Toxicity/PII/Prompt Injection 不在本任务范围内）：

- **Tool Selection Quality**（工具选择质量，span 级）
- **Action Advancement**（任务推进度，trace 级）
- **Action Completion**（任务完成度，session 级）
- **Agent Efficiency**（执行效率，session 级）
- **Correctness**（正确性/事实性，结果级）
- **Instruction Adherence**（指令遵循，结果级）

这六个指标覆盖了 span / trace / session 三种判定粒度，也覆盖了 Agent 任务达成类与响应质量类两大类别，具备代表性，且均属于"可以用是/否或有限类别回答的判断题"，符合 Luna-2 论文中"单 token 分类范式适用的指标类型"。

### 任务描述

需要实现面向上述六个指标的评测小模型，且该评测小模型需要以可插拔评估器的形式集成到 Agent Insight 平台的评测体系中（对接 `src/lib/evaluators/` 评估器注册与执行链路），使平台用户可以在实际评测流程中选用该小模型作为 LLM Judge 之外的评测方式，具体需求如下：

1. **单 token / 确定性分类范式**：对六个指标均需实现"输入待评测内容与判定依据 → 单次前向 → 在类别 token（如 true/false，或对应指标的多类别 token）上做归一化 → 输出确定性判定 + 置信度分数（0～1）"的评测方式，不得依赖多 token 自由生成或采样得到结果；对同一输入重复评测，应得到完全一致的判定结果。

2. **共享骨干 + 指标级轻量适配器**：六个指标应共享同一个基座小模型（骨干可自选，如 Qwen / Llama / Mistral 等开源小模型，参数量不做强制要求），每个指标以独立的轻量适配器（LoRA 或等价的低参数量微调方式）实现，不要求为每个指标训练独立的完整模型；应支持在同一批推理中并发激活多个指标的适配器，避免"跑 1 个指标"与"跑 6 个指标"的延迟出现数量级差异。

3. **六个指标的输入模板与判定粒度**：需要分别为以下六个指标定义评测所需的输入内容（判断题描述 + 被评测内容 + 判定所需参考信息）：
   
   - **Tool Selection Quality**：给定一次工具调用（用户意图、可用工具/参数清单、Agent 实际选择的工具与参数），判定该次工具选择是否与用户意图一致；
   - **Action Advancement**：给定某一执行步骤及其上下文，判定该步骤是否朝用户目标产生了有效推进；
   - **Action Completion**：给定一次完整会话的全部用户目标与全部执行步骤，判定该会话是否达成了用户提出的**所有**目标；
   - **Agent Efficiency**：给定一次完整会话的执行步骤序列，判定该会话在达成目标的过程中是否存在明显冗余或无效步骤；
   - **Correctness**：在不依赖参考答案（reference-free）的前提下，判定 Agent 最终输出是否存在与已知信息相悖的事实性错误（开域幻觉，区别于依赖检索上下文判断的忠实度/Context Adherence）；
   - **Instruction Adherence**：判定 Agent 最终输出是否遵循了用户或系统指令中提出的约束。
   
   六个指标中，Tool Selection Quality / Action Advancement 判定粒度到单步或单次工具调用，Action Completion / Agent Efficiency 判定粒度到整段会话（多步骤聚合），Correctness / Instruction Adherence 判定粒度到最终结果，需分别按对应粒度组织输入。

4. **输出与平台可对接**：每个指标的输出应包含"判定结果（True/False 或类别）+ 置信度/风险分（0～1，可映射为 0～100）"，输出结构应能够与平台现有评估器结果结构（`TraceEvaluator` / `EvalResult`，含 `metricKey`、`score`、`confidence`、`method` 等字段，详见质量监控设计规格 §3.1）兼容或经少量字段映射后对接，验证小模型评测器具备作为平台"可插拔评估器"运行的可行性（不要求真正合入 `src/lib/evaluators/` 生产代码，验证接口/输出结构可映射即可）。

5. **训练数据构造**：需要说明六个指标各自训练/验证数据的构造方式（人工标注、合成生成、Agent Insight 平台已采集的第三方 Agent Trace、公开数据集等，任选其一或组合均可），并保证训练集与测试集之间不发生同一交互的近重复泄漏。

6. **与 LLM Judge 基线的对比**：需要选定至少一个可作为对照的 LLM Judge 基线（可以是平台现有的 preset 评估器，如"指令遵循""结果准确性""Agent 轨迹质量"等，也可以是自行调用的通用大模型 Judge），在准确率、成本、延迟、确定性四个维度给出量化对比（具体验收指标见下节）。

### 验收方法

验收应覆盖以下方面，具体验收数据集与验收用例由学生自行设计与构造（可基于平台已采集的第三方 Agent Trace，或复用/构造公开的 Agent 评测数据集，如 BFCL、Who&When 等含工具调用/多步执行的数据）：

1. **确定性验证**：对同一批输入（覆盖六个指标）分别重复评测 N 次（N ≥ 5），验证同一输入在不同次评测下的判定结果是否保持完全一致。

2. **精度验证**：在六个指标各自的验证集上，分别给出小模型判定结果相对人工标注或 LLM Judge 基线的一致率（F1 或准确率），并说明与 LLM Judge 基线的量化差距（不要求严格超过基线，但应给出具体数字而非定性描述）。

3. **成本与延迟验证**：给出小模型评测器与所选 LLM Judge 基线在同等评测任务下的单次评测延迟（如 P50/P95）与千次评测成本估算对比数据。

4. **共享骨干有效性验证**：对比"仅跑 1 个指标"与"六个指标全部跑一遍"的端到端延迟，验证延迟增幅是否明显小于按指标数线性叠加（若延迟随指标数近似线性增长，视为未达成共享骨干设计意图）。

5. **平台兼容性验证**：验证小模型评测器对六个指标的输出，能够直接或经少量字段映射后转换为与平台 `EvalResult` 结构兼容的形式，并给出至少一条端到端示例（输入某条 Trace/Session → 输出该结构）。

验收时应明确说明所依据的具体输入材料（训练/验证数据来源、LLM Judge 基线选择、验收环境与硬件配置）与验收环境，并针对上述各项要求逐一说明满足情况及依据。

### 完成度标准

对学生的任务完成度按高、中、低三档评估，沿用验收方法中的五个维度，逐项判断达成程度，再综合得出总体档位。

**确定性**

- 高：六个指标在重复评测（N ≥ 5）下判定结果均完全一致，无任何波动。
- 中：绝大多数样本重复评测结果一致，但存在少量样本出现波动。
- 低：判定结果随评测次数明显波动，与常规 LLM 生成式打分相比未体现出确定性优势。

**精度**

- 高：六个指标相对人工标注/LLM Judge 基线的一致率（F1/准确率）均给出量化结果，且多数指标与基线差距较小（基本持平或差距可控）。
- 中：给出了量化结果，但部分指标与基线差距明显，或仅覆盖六个指标中的一部分。
- 低：未给出可信的量化精度对比，或精度结果与基线相比明显不可用（如接近随机猜测水平）。

**成本与延迟优势**

- 高：给出了小模型与 LLM Judge 基线的成本、延迟量化对比，且小模型在两项上均体现出明显优势；同时验证了共享骨干使多指标并发的延迟增幅明显小于线性叠加。
- 中：给出了成本或延迟其中一项的量化优势，但另一项优势不明显或未验证；或共享骨干的延迟增幅接近线性但仍具备一定优势。
- 低：未给出可信的成本/延迟量化对比，或小模型方案相对 LLM Judge 基线未体现出成本/延迟优势。

**平台兼容性**

- 高：小模型评测器对六个指标的输出均能直接或经少量映射对接到平台 `EvalResult` 结构，并给出可运行的端到端示例。
- 中：部分指标的输出结构可对接，但存在字段缺失或需要较多改造才能对接的情况。
- 低：输出结构与平台评估器结构差异较大，未说明或未验证可对接性。

**综合定档规则**

以"确定性"与"精度"两个维度作为核心判定依据，对应 Luna-2 方案最核心的价值主张——用确定性单 token 判定替代非确定性生成式打分，且精度不能明显劣于 LLM Judge 基线，其余维度作为辅助判定：

- 高：核心两个维度均达到高档，其余维度不低于中档。
- 中：核心两个维度均不低于中档，或其中一个维度为高档、另一个不低于中档，其余维度允许存在低档。
- 低：核心两个维度中至少一个为低档，或多数维度整体处于低档。

## 任务七：基于成功轨迹的Agent长程任务漂移故障检测

### 任务背景

Agent 执行复杂长程任务时，失败定位极其困难：轨迹常含数十至上百个步骤，真正的错误步骤往往被后续在错误基础上继续执行的步骤掩盖，人工通读排查动辄数小时。现有自动化路线均存在结构性局限——提示式分析管线反复调用前沿大模型逐步审查，token 与延迟成本高，实时诊断无法落地；有监督后训练依赖"哪一步出错"的步骤级标注，既昂贵又带主观歧义，且多数方法只考虑单步干预，无法刻画多步骤共同导致失败的复合错误。公开基准测评显示，即便是最新的大模型，自动定位失败步骤的准确率也相当有限。

一条值得注意的思路，是反过来利用"成功"而非"失败"来诊断故障。失败轨迹需要人工标注出错步骤，成本高且主观；而成功轨迹是系统正常运行的天然副产物，几乎零成本就能大量获得，且天然刻画了"正常执行应该是什么样"。如果能让模型只从成功轨迹中学习正常执行的行为模式，再拿一条失败轨迹来比对、找出其中偏离正常模式最远的那些步骤，就不必再依赖昂贵的失败标注。arXiv:2607.12747 所提出的 Oat（无监督 Trace 异常定界）正是这类思路的代表：它从"正常执行"本身学习内在的动态规律，遇到失败轨迹时，通过度量每个步骤相对正常模式的偏离程度来定位问题步骤，据此还原出"哪些步骤推动了失败"。相比需要反复调用大模型的做法，这种方式推理开销极低，因而具备在线诊断的可行性。

本任务的核心命题是 **Agent 漂移故障检测**：将 Agent 的失败视为执行行为偏离正常动态模式的结果——漂移（Drift）指执行逐步脱离由成功轨迹刻画的正常执行模式，可能体现为单步异常动作，也可能体现为多步渐进偏离目标路径并逐级放大。与根因分析回答"为什么会失败"不同，漂移检测刻画"正常应该是什么样"并识别"哪一步偏离了正常"，以极低推理成本与延迟完成故障步骤定位，具备对执行中轨迹实时或近实时诊断的可行性。要求参考 Oat 的无监督范式，独立探索并实现一套面向 Agent 执行轨迹的漂移故障检测机制，重点验证"无需失败标注、仅从成功轨迹学习"即可完成漂移步骤检测与定位；具体技术路线由学生自行选择。

### 任务描述

需要实现面向 Agent 执行轨迹的漂移故障检测能力——以 Agent 行为相对正常执行模式的漂移作为故障检测与定位的核心对象，具体需求如下：

1. **无监督漂移建模**：训练阶段应仅使用成功轨迹，不使用任何步骤级错误标注，学习 Agent 正常执行行为的内在动态模式并以此作为漂移检测基线；应说明训练数据的来源与规模，并验证模型确实刻画了成功轨迹的动态模式，而非退化为简单规则或对样本的记忆。

2. **漂移检测**：针对一条待检测的执行轨迹，应能判定其是否存在漂移——给出"存在漂移/正常"的检测结论与可量化的漂移程度评分，并明确判定所依据的阈值或规则；对未发生漂移的正常轨迹应能正确放行，避免将正常执行误判为漂移。

3. **步骤级漂移定位**：针对一条失败轨迹，应能定位并输出导致任务失败的漂移步骤集合（即故障贡献步骤，论文原称 failure contributing steps）——指显著推动轨迹走向失败的步骤，不限于最早出错、也不要求单靠该步骤即可导致失败；同时应为轨迹中每个步骤给出可量化的漂移/异常程度评分，作为判定依据。

4. **轨迹动态刻画**：应能够处理变长、不规则结构的轨迹；应能够刻画"同一目标存在多条成功路径"的行为多样性，不应将偏离某一条固定路径、但仍属正常范围的执行步骤误判为漂移。

5. **推理轻量化**：推理阶段不应依赖前沿大模型对轨迹进行逐步审查，应达到轻量、低延迟、低（或零）token 成本的检测能力，具备对执行中轨迹进行实时或近实时诊断的可行性。

6. **可追溯与可解释**：每条漂移判定应能够关联到具体轨迹步骤及其判定依据（如该步骤相对正常动态模式的偏离程度），支持人工对检测结果进行核实与确认。

### 验收方法

验收数据集建议以 MCP-Atlas（其成功轨迹用于训练、失败轨迹用于验证）与 Who&When 为主，两者均提供已知的故障步骤标注（ground truth）；学生可自行补充或构造其他带步骤级标注的 Agent 轨迹数据集，具体验收场景与验收用例由学生自行设计与构造，验收应覆盖以下方面：

1. **无监督漂移建模能力**：验证模型是否在仅提供成功轨迹（不含任何步骤级错误标注）的条件下完成训练，并验证其对正常多路径成功行为的刻画——即对偏离单一固定路径但仍属正常的执行方式不会误报为漂移（覆盖任务描述中的"轨迹动态刻画"要求；属建模质量层面的验证，与第 2 项的检测判定层面相区分）。

2. **漂移检测能力**：在包含正常（成功）轨迹与发生漂移的故障轨迹的混合样本上，验证模型能否正确区分二者，给出检测判定的量化指标（如准确率、召回率、精确率或误报率），确认对正常轨迹不会系统性误报为漂移，并说明检测结论与步骤级定位结果的衔接关系。

3. **步骤级漂移定位能力**：在带已知故障步骤标注的失败轨迹上验证步骤级定位效果，确认模型能够输出漂移步骤集合，给出相对 ground truth 的量化指标（如 F1、准确率），并与至少一个提示式 LLM 基线进行量化对比，说明差距或优势。

4. **复合错误处理**：验证对由多个步骤共同导致失败的轨迹的定位效果，确认能够输出完整的多个漂移步骤，而非仅返回单个"最早错误"步骤。

5. **效率**：给出与提示式 LLM 基线的推理延迟与成本量化对比，验证推理过程不依赖前沿模型逐步审查。

6. **结果一致性与可追溯性**：验证对同一条故障轨迹进行多次独立检测，输出的漂移步骤集合与评分保持一致，且判定可关联到具体步骤与依据。

验收时应明确说明所依据的具体输入材料（成功轨迹与故障轨迹数据集、ground truth 标注来源、提示式基线选择等）与验收环境，并针对上述各项要求逐一说明满足情况及依据。

### 完成度标准

对学生的任务完成度按高、中、低三档评估，沿用验收方法中的六个维度，逐项判断达成程度，再综合得出总体档位。

**无监督漂移建模能力**

- 高：在仅使用成功轨迹、无任何步骤级标注的条件下完成训练，建模结果能够准确刻画正常执行动态（包括对变长、不规则轨迹的处理与多路径成功行为的刻画），训练数据的来源与规模说明充分。
- 中：能够基于成功轨迹完成训练，但建模质量一般，或对多路径成功行为的刻画不完整，或训练数据说明不充分。
- 低：训练依赖了失败轨迹或步骤级标注，或模型退化为简单规则/记忆，未真正学习成功轨迹的动态模式。

**漂移检测能力**

- 高：在混合正常轨迹与漂移轨迹的样本上给出可信的量化检测指标，能够准确区分正常轨迹与发生漂移的轨迹，对正常轨迹误报率低，且检测结论与步骤级定位结果衔接一致。
- 中：能够给出检测判定与量化指标，但存在明显的漏报或误报，或检测与定位的衔接关系不清晰。
- 低：无法有效区分正常轨迹与漂移轨迹，检测结果接近随机水平，或未给出可信的量化评估。

**步骤级漂移定位能力**

- 高：给出相对 ground truth 的量化指标，能够准确识别故障轨迹中的漂移步骤，且与提示式 LLM 基线相比具有明确优势或基本持平，能覆盖不同长度与复杂度的轨迹。
- 中：给出了量化指标，能识别出部分漂移步骤，但相对基线存在明显差距，或仅在部分简单场景下有效。
- 低：漂移步骤定位结果大量错误，与随机水平相当，或未给出可信的量化评估。

**复合错误处理**

- 高：能够准确识别由多个步骤共同导致失败的复合错误，输出完整且正确的漂移步骤集合，无明显遗漏或过度。
- 中：能够识别部分漂移步骤，但存在明显遗漏或误报。
- 低：仅能处理单一错误步骤的场景，无法正确输出多个漂移步骤。

**效率**

- 高：给出与提示式 LLM 基线的延迟、成本量化对比，推理不依赖前沿模型逐步审查，体现出明显（如数量级）的效率优势。
- 中：给出了对比数据，但优势有限，或未与前沿模型基线形成有效对比。
- 低：推理仍依赖大模型逐步审查，或未给出可信的效率评估。

**结果一致性与可追溯性**

- 高：对同一故障轨迹多次检测结果完全一致，且每条判定均可关联到具体步骤与依据，可被人工核实。
- 中：绝大多数样本结果一致，个别样本存在波动，或可追溯性不完整。
- 低：结果随检测次数明显波动，或判定缺乏可追溯依据。

**综合定档规则**

以"漂移检测能力"与"步骤级漂移定位能力"两个维度作为核心判定依据，对应本任务最核心的价值主张——Agent 漂移故障检测既要能准确识别轨迹中是否存在漂移，又要能定位到实际发生漂移的具体步骤，其余维度作为辅助判定：

- 高：核心两个维度均达到高档，其余维度不低于中档。
- 中：核心两个维度均不低于中档，或其中一个维度为高档、另一个不低于中档，其余维度允许存在低档。
- 低：核心两个维度中至少一个为低档，或多数维度整体处于低档。

## 任务八：多Agent协同漂移的建模、检测与根因诊断

### 任务背景

多智能体 LLM 系统日趋成熟，越来越多地承担起复杂任务的分解与协同求解：一个编排节点把整体目标拆解成若干子任务，交给各司其职的专业 Agent，Agent 之间再通过消息往来、共享记忆与协作规程共同完成目标。人们习惯用"能否正确完成任务"来评判这类系统，却很少关心另一个同样重要的问题——同一个系统在持续运行、经历大量交互之后，其行为方式是否还和最初设计时保持一致。而这恰恰是它最脆弱的地方。

Agent 的行为并非一成不变，而是在长期交互中会发生缓慢而隐蔽的"漂移"：系统没有被人为修改任何参数、提示词或代码，也没有出现任何显式报错，它的决策模式却一点点偏离了最初的设定。这种偏离往往先从一个不起眼的环节开始，比如某个负责分派的 Agent 开始不自觉地偏重某一类子 Agent，某个 Agent 的输出措辞逐渐偏离原始任务意图，或 Agent 之间的协作产生冗余往返。单独看每一次交互，这些变化几乎无法察觉；但它们会悄然累积并互相放大，最终显现为整体任务完成质量的明显下降。传统软件也有退化机制（如内存泄漏、配置漂移），这些已被成熟的运维手段所覆盖；而 LLM Agent 的这类行为漂移属于全新的失效模式，尤其当偏差源于 Agent 之间未被显式设计过的交互时，既难被单点监控所捕获，也难凭经验人工识别。

问题之所以棘手，在于它缺少一套"度量语言"：直觉上我们知道系统"变差"了，却说不清差在哪、差到什么程度、从哪一刻开始，也就无从预警和治理。因此需要为多智能体系统建立行为稳定性的量化刻画——把漂移分解为若干可观测、可计算的维度，合成一个随运行时间演变的稳定度指标，再借由对稳定基线的偏离来及时察觉漂移的发生。arXiv:2601.04170 所提出的 Agent Stability Index（ASI，多智能体行为稳定性指数）即是这样一种探索：它不把漂移当作笼统的整体劣化，而是从单体行为、工具使用、智能体间协同等不同侧面分别度量，再复合为一个综合指数用于漂移检测。

本任务的核心命题，正是要独立完成这样一套 **多 Agent 协同场景下的漂移故障处理机制**：不是对单条失败轨迹做事后定位，而是在系统持续运行的过程中，通过多维度、跨时段的量化建模，先刻画"稳定时是什么样"，再持续感知"现在偏离了多少"，并进一步诊断"漂移因何而起"——既要能捕捉单个 Agent 的行为漂移，更要能刻画智能体之间协同关系的退化（共识松动、交接低效、分工崩坏），因为协同关系的劣化正是多智能体系统区别于单 Agent 最本质、也最容易被忽视的失效来源。具体如何划分维度、定义指标、设定权重与检测阈值，均由学生自行设计。

### 任务描述

需要实现面向多智能体协同场景的漂移故障处理能力，始终以"多 Agent 协同"为视角——既要度量单个 Agent 的行为漂移，更要刻画智能体之间协同关系的退化（共识松动、交接低效、分工崩坏）。具体需求如下：

1. **漂移类型建模**：应能对多智能体协同场景下的漂移进行类型化刻画，至少覆盖语义漂移（输出逐步偏离原始任务意图而句法仍合法）、协调漂移（多智能体共识机制退化、冲突与冗余增多、交接与分工失效）、行为漂移（涌现出初始交互中不存在的新策略或动作模式）三类，并重点刻画协同类漂移（协调漂移）的典型形态；给出区分各类型所依据的可操作判定规则。

2. **多维复合度量与协同刻画**：应构建覆盖多个行为维度、分门别类的复合漂移指标（可参考 ASI 的响应一致性、工具使用模式、智能体间协调、行为边界四大类），每个维度应有明确的计算方法与归一化方式，并说明各维度/类别在合成总指标时的权重设定依据；在此基础上，除度量单体 Agent 的行为偏差外，必须显式刻画智能体之间的协同退化，包括但不限于多智能体决策的共识一致率、Agent 间任务交接效率、角色分工的维持程度（或等价指标）。这是"多 Agent 协同"区别于单 Agent 漂移检测的核心。

3. **漂移检测**：应在持续运行的交互序列上，通过滑动窗口等时序机制计算漂移指标，并基于阈值规则判定漂移是否发生（如连续若干个窗口跌破阈值），输出可解释的告警；检测机制应能识别漂移的起始时点，并尽可能标识所涉及的漂移类型或主导维度。同时应说明稳定基线如何建立（如以最初若干次交互为基线），并对检测的灵敏度与误报率进行平衡——对属正常范围内的行为波动不应频繁误报，对真实漂移不应漏报。

4. **根因诊断**：在检测到漂移发生后，应能进一步诊断漂移的根因——定位到具体涉及的 Agent、交互环节或协同关系（而非仅停留在"发生了漂移"的层面），区分根因与其下游的漂移表现，输出可操作的结构化诊断结论。

5. **可追溯性**：每条漂移告警与诊断结论都应能定位到具体的时间窗口、所涉及的维度/指标、驱动其劣化的交互片段或 Agent，使判定与诊断可被人工核实。

6. **缓解机制（可选加分项，不纳入定档）**：可在检测与诊断基础上探索漂移缓解策略（如情景记忆整合、漂移感知路由、自适应行为锚定等），并说明其相对未干预对照组的漂移削减效果与额外开销。

### 验收方法

验收数据集以多智能体系统在长期交互序列上的行为日志为基础，应自行构造或改造多智能体交互序列数据，覆盖不同任务域、不同交互长度（如几十到上千次交互），并注入或自然呈现语义/协调/行为三类漂移，记录漂移的起始时点与类型、以及根因（涉及的具体 Agent 或协同环节）作为 ground truth，分别用于漂移类型建模、检测与根因诊断的评估。具体验收场景与验收用例由学生自行设计与构造，验收应覆盖以下方面：

1. **漂移类型建模与区分**：验证对语义漂移、协调漂移、行为漂移三类（或学生扩充的更多类型）能够给出清晰的定义与可操作的区分规则，在构造的含标注漂移样本上，建模结果与 ground truth 一致。

2. **多维复合度量与协同刻画有效性**：验证所构建的各维度指标能够随注入的漂移呈现可预期的单调变化趋势，且不同维度对不同类型漂移的敏感程度与预期一致（如协调漂移主要触动协同维度指标而非工具选择指标）；验证对多智能体共识、交接、分工退化的量化刻画有效，能够检测出仅靠单体行为度量无法发现的协调漂移。

3. **漂移检测能力**：在含漂移交互序列上，验证检测机制能够以可接受的准确率/召回率识别漂移的发生，并正确标识漂移起始时点与主导类型/维度，给出相对 ground truth 的量化指标；同时验证在稳定（无漂移）交互序列上误报率处于可接受水平，不会因正常行为波动频繁触发告警，并说明检测阈值与灵敏度设定的依据。

4. **根因诊断能力**：验证在漂移发生后，系统能够进一步定位根因——正确识别涉及的 Agent、交互环节或协同关系，区分根因与下游漂移表现，并输出结构化、可操作的诊断结论；在构造的含根因标注样本上，诊断结果与 ground truth 一致，并给出量化指标。

5. **可追溯性**：验证每条漂移告警与诊断结论能够关联到具体时间窗口、维度指标与交互片段，可被人工核实。

6. **缓解效果（可选加分项，不纳入定档）**：验证缓解策略相对未干预对照组的漂移削减效果，并说明引入的额外计算/延迟开销。

验收时应明确说明所依据的具体输入材料（多智能体交互序列数据集、漂移注入方式与 ground truth 标注来源等）与验收环境，并针对上述各项要求逐一说明满足情况及依据。

### 完成度标准

对学生的任务完成度按高、中、低三档评估，沿用验收方法中的五个核心维度（缓解机制为可选加分项，不纳入定档），逐项判断达成程度，再综合得出总体档位。

**漂移类型建模**

- 高：给出清晰、可操作的类型定义与区分规则，覆盖三类及以上漂移表现，且在含标注样本上建模准确、边界清晰。
- 中：给出类型定义，但区分规则较模糊，或在部分类型上存在误分。
- 低：漂移类型定义不清，或无法在样本上实现有效区分。

**多维复合度量与协同刻画**

- 高：构建了覆盖多个类别与行为维度的复合指标，每个维度有明确计算与归一化方式，权重设定有依据，指标随漂移呈现可预期的单调变化；并显式刻画多智能体共识、交接、分工等协同退化，能检测出仅靠单体度量无法发现的协调漂移。
- 中：构建了多维指标，但部分维度定义模糊、归一化或权重设定缺乏依据，指标灵敏度一般，或对协同退化的刻画不完整。
- 低：指标维度单一或定义不清，无法有效量化漂移；或未刻画智能体间协同关系，仅度量单体行为，偏离"多 Agent 协同"的核心定位。

**漂移检测**

- 高：能在长时间交互序列上以可接受的准确率/召回率检测漂移，正确定位起始时点与主导类型，阈值选择有依据；且在稳定交互序列上误报率低，对真实漂移漏报少，检测灵敏度有明确的设计与调优说明。
- 中：能检测出漂移，但在起始时点定位或类型判别上存在偏差，或存在较明显的误报/漏报。
- 低：检测结果与随机水平相当，或频繁误报、严重漏报，检测不可用。

**根因诊断**

- 高：在漂移发生后能准确定位根因——正确识别涉及的 Agent、交互环节或协同关系，区分根因与下游漂移表现，诊断结果与 ground truth 高度一致并给出量化指标。
- 中：能定位到大致范围或部分涉及的环节，但根因定位不精确，或未有效区分根因与下游表现。
- 低：仅能报告"发生了漂移"，未能进一步诊断根因，或诊断结果与 ground truth 严重不符。

**可追溯性**

- 高：每条告警与诊断结论可定位到具体时间窗口、维度指标与交互片段，可被人工核实，判定依据清晰。
- 中：能定位到大致时间范围或维度，但无法精确到具体交互片段。
- 低：无法说明告警或诊断的判定依据。

**综合定档规则**

以"多维复合度量与协同刻画""漂移检测""根因诊断"三个维度作为核心判定依据，其余维度作为辅助判定：

- 高：三个核心维度均达到高档，其余维度不低于中档。
- 中：三个核心维度均不低于中档，或其中至少一个为高档、其余不低于中档，其余维度允许存在低档。
- 低：三个核心维度中至少一个为低档，或多数维度整体处于低档。

## 任务九：Agent Orchestrator（工作流编排、运行控制与回放调试）

### 任务背景

AET 通过多个领域 Agent 与编排 Skill 协作完成需求分析、功能设计、开发计划、代码实现、测试验证和交付等研发活动。工作流中的阶段顺序、Agent、步骤和人工确认点可以通过配置调整，长程任务还可以借助 Checkpoint 保存和恢复执行进度。这些能力为不同项目定制研发流程提供了基础。

但从开发者使用角度看，工作流的配置、执行和调试仍是三个相互割裂的过程。配置阶段需要理解多层配置的覆盖关系和具体字段；执行阶段需要从命令输出、日志及产物目录中判断当前进度；发生异常后，又需要人工还原 Agent、Skill、工具调用、人工确认和工件变化之间的先后关系。开发者能够启动工作流，并不等于能够快速回答“实际生效的是哪份配置”“当前为什么暂停”“这个步骤失败后应该从哪里继续”等问题。

手工编辑配置还存在另一类风险。开发者通常以“在 PR 前增加安全检查”“需求设计完成后必须人工确认”等业务语言描述流程调整，但这些意图需要被准确转换为配置变更。如果系统直接根据自然语言修改配置而不展示差异、处理歧义或等待确认，错误的流程调整可能绕过必要的评审节点，或者改变原本无关的配置。

工作流调试同样不能简单等同于“重新运行一次”。Issue、PR、Release 等操作可能产生外部副作用；从失败步骤恢复或从历史节点分叉调试时，如果重复执行已经完成的操作，可能产生重复数据或影响真实项目。因此，需要一个统一的 Agent Orchestrator，将工作流的可视化编排、运行控制、人工确认、历史回放和分叉调试放在同一个界面中，同时保证生成配置可执行、运行状态可信、调试操作与真实副作用隔离。

本任务的重点是围绕 AET 已有能力构建开发者工作台，不要求重新实现 AET 的 Agent、Skill 或工作流执行引擎。具体前端形态可以是 Web、桌面应用或其他图形界面，但必须与真实 AET 工作流完成端到端对接。

### 任务描述

需要实现面向 AET 工作流的图形化编排、运行控制与回放调试能力，具体需求如下：

1. **工作流可视化编排**：应能够以图形方式展示和编辑工作流中的阶段、Agent、步骤、Skill、Hook 及其执行关系，使使用者可以完成新增、删除、移动和配置等操作；界面中的节点与连接必须对应明确的 AET 配置实体，不能只生成无法执行的示意图。

2. **现有配置导入与最终配置展示**：应支持导入已有 AET 工作流配置并还原为可编辑视图；当配置来自不同层级时，应能够展示配置的来源、覆盖关系及最终生效结果，使使用者可以判断某个节点或属性由哪一层配置决定。

3. **配置导出与往返一致性**：从界面生成的配置应能够被 AET 直接加载，或经过明确且固定的转换后加载；对一份现有配置执行“导入—查看或编辑—导出”后，未被修改部分的语义应保持不变，不能因字段顺序、默认值填充或界面模型不完整而产生行为变化。

4. **自然语言辅助修改**：应支持使用自然语言描述常见的工作流调整，并将其转换为结构化配置补丁；系统必须同时展示工作流视图变化和配置差异，说明新增、删除、移动或修改了哪些内容；存在歧义、冲突或超出支持范围的请求时，应要求使用者澄清或明确拒绝执行，不能静默猜测；所有修改必须在使用者确认后生效，并支持撤销。

5. **配置校验与试运行**：应在真实执行前检测未定义 Agent 或 Hook、断开的执行关系、不可达步骤、缺少必要输入工件、配置覆盖冲突等问题；应提供不调用模型、不写入外部平台的试运行能力，展示预计执行顺序、人工确认点、输入输出工件和可能阻塞的位置。

6. **运行状态可视化**：工作流执行期间，应实时展示当前阶段、Agent、步骤、输入输出工件、开始时间、执行时长和状态；至少应区分等待执行、执行中、等待人工确认、暂停、失败、恢复中、已终止和已完成等状态；页面刷新、客户端重连或多个视图同时打开时，界面状态应以后台真实状态为准。

7. **运行控制与人工确认**：应支持暂停、继续、终止和失败步骤重试，并正确处理 AET 的人工确认点；需要人工确认的步骤不能因刷新页面、调用接口或修改前端状态而被绕过；对终止、重新执行和可能产生外部影响的操作，应展示影响范围并要求明确确认。

8. **执行历史与时间线回放**：应记录并按时间线展示用户输入、Agent 输出、Skill 调用、工具调用、Hook、Checkpoint、状态变化和工件变化，使使用者可以定位一次运行中发生了什么；回放内容应来自真实执行记录，并能够关联到对应的原始数据或工件版本。

9. **分叉调试与运行对比**：应支持从一个允许恢复或调试的历史节点创建独立分支，修改后续输入、配置或其他允许调整的条件，再执行后续步骤；原始运行记录不得被覆盖；系统应能够比较原始运行与调试运行的步骤、工件、耗时、错误和最终结果，并标出最早出现差异的位置。

10. **外部副作用隔离**：回放和分叉调试默认不得重复创建或修改真实 Issue、PR、Release 等外部对象；对于无法安全模拟或无法保证幂等的操作，应使用已有结果、模拟返回或人工确认，并在界面中明确标识；系统应保存操作是否真实执行、被复用、被模拟或被跳过的记录。

11. **使用效果评估**：应设计固定的编排和调试任务，对比 Agent Orchestrator 与直接使用配置文件、命令行和日志时的任务完成率、完成时间、操作步骤、配置错误数或故障定位时间；不能仅以界面是否完成或主观观感作为易用性结论。

### 验收方法

验收应覆盖以下方面，具体验收工作流、故障注入方式与测试用例由学生自行设计与构造：

1. **配置导入导出验证**：准备包含不同阶段、Agent、步骤和 Hook 的工作流配置，验证导入后能否正确还原；在不修改配置的情况下重新导出，比较导出前后的有效语义；在界面完成修改后，验证生成配置能否由 AET 加载并按预期顺序执行。

2. **多层配置解析验证**：准备存在覆盖关系的多层配置，验证界面能否准确展示各字段来源、覆盖关系和最终生效值；修改任一层后，最终工作流视图应正确更新。

3. **自然语言修改验证**：构造新增步骤、删除步骤、移动节点、修改 Hook、调整 Agent 等不同类型的请求，同时包含明确请求、歧义请求、冲突请求和超出范围请求；验证配置补丁是否准确、无关字段是否保持不变、系统是否在需要时要求澄清，以及未经确认的修改是否不会写入。

4. **配置校验与试运行验证**：构造未定义节点、断链、不可达步骤、工件缺失和覆盖冲突等错误配置，验证系统能否在执行前识别并定位；验证试运行不会调用模型、修改代码或操作外部平台，同时能展示完整的预计执行路径。

5. **运行状态一致性验证**：执行一条包含多个 Agent、人工确认点和工件传递的真实 AET 工作流，对照后台事件和持久化状态，逐项核验界面显示；在页面刷新、网络短暂中断和客户端重连后，状态应能够恢复且不出现虚假的完成或失败状态。

6. **运行控制验证**：分别在普通步骤、人工确认点和失败步骤执行暂停、继续、拒绝、终止和重试操作，验证后台状态转换、界面反馈和后续执行路径是否正确；构造绕过前端直接调用接口的情况，验证必要的人工确认仍然有效。

7. **故障恢复验证**：在 Agent 执行、工具调用、工件写入和外部平台操作前后注入中断或失败，验证系统能否从正确位置继续；已经完成的外部操作不得被重复执行，部分完成的操作必须被识别并给出处理方式。

8. **回放与分叉验证**：选择一条包含失败和恢复过程的历史运行，验证时间线能否完整还原；从指定节点建立调试分支并修改一个条件，验证原始记录保持不变，调试分支可以独立运行，并能正确标出两次运行最早出现差异的位置。

9. **副作用隔离验证**：在回放和分叉调试中加入创建 Issue、更新 PR 或发布 Release 等操作，验证默认情况下不会对真实外部对象执行重复写入；所有复用、模拟、跳过和真实执行状态都应可核实。

10. **开发者体验验证**：选择若干具备基本开发经验、但不熟悉该界面的参与者，分别使用 Agent Orchestrator 和原有命令行方式完成同一组编排、状态判断和故障定位任务；记录任务完成率、完成时间、操作错误和求助次数，并说明实验条件与样本限制。

11. **AET 集成验证**：在真实 AET 项目环境中完成“导入或创建工作流—试运行—启动执行—人工确认—发生失败—恢复或分叉调试”的端到端演示，验证系统使用的是 AET 的真实配置、事件、Checkpoint 和执行结果，而非独立构造的一套演示数据。

验收时应明确说明 AET 版本、工作流配置、外部平台或模拟环境、故障注入点、参与者背景及测试数据，并针对上述要求逐一说明满足情况及依据。

### 完成度标准

对学生的任务完成度按高、中、低三档评估，沿用验收方法中的五个维度，逐项判断达成程度，再综合得出总体档位。

**工作流编排与配置一致性**

- 高：能够完整导入、展示和编辑 AET 工作流，准确解释多层配置覆盖关系；导入导出保持语义一致，生成配置可由真实 AET 执行；对常见错误配置能够在执行前准确定位。
- 中：能够完成主要工作流的导入、编辑和导出，生成配置基本可执行，但对部分配置实体、覆盖关系或错误类型支持不完整，偶尔需要人工修改配置才能运行。
- 低：界面只能绘制流程示意图，无法稳定导入现有配置或生成可执行配置，或导入导出后工作流行为发生明显变化。

**运行状态与控制可靠性**

- 高：界面状态与后台真实状态保持一致，刷新和重连后能够正确恢复；暂停、继续、终止、重试和人工确认均能驱动正确的后台状态转换，必要确认无法被绕过。
- 中：主要状态和控制操作基本可用，但在重连、异常状态或部分控制操作下存在显示延迟、状态不同步或需要人工干预的问题。
- 低：界面状态主要由前端自行维护，与真实工作流经常不一致，或控制操作不能可靠影响后台执行，人工确认存在被绕过的情况。

**回放调试与副作用隔离**

- 高：能够基于真实记录完整回放运行过程，从安全节点创建独立调试分支，准确比较两次运行并定位首个差异；回放和调试不会重复产生外部副作用，相关处理均有可追溯记录。
- 中：具备基本时间线和分叉能力，但部分事件或工件变化无法还原，对比结果不完整，或仍有少量外部操作需要人工保证安全。
- 低：只能展示普通日志，无法从历史节点分叉调试，原始记录可能被覆盖，或回放会重复执行真实外部操作。

**自然语言修改的准确性与安全性**

- 高：对支持范围内的修改请求能生成准确、最小化的配置补丁，能够识别歧义和冲突，所有变更均经过差异展示和用户确认，且支持可靠撤销。
- 中：常见修改基本准确，但对复杂请求的处理不稳定，可能产生少量无关变更，或澄清、确认和撤销机制存在局限。
- 低：自然语言修改经常产生错误配置或改变无关字段，存在歧义时仍直接写入，或缺少确认和撤销机制。

**开发者体验与真实集成**

- 高：与原有配置文件、命令行和日志方式相比，在任务完成率、完成时间、错误数或定位时间中的多个指标上体现出可复现的改进；在真实 AET 环境中完成端到端流程。
- 中：完成了真实 AET 对接，并在至少一个开发者体验指标上有所改进，但实验规模较小、结果波动较大，或部分环节仍依赖演示数据。
- 低：主要基于静态原型或模拟数据，无法完成真实 AET 工作流，或未提供可核实的开发者体验对比。

**综合定档规则**

以“工作流编排与配置一致性”和“运行状态与控制可靠性”两个维度作为核心判定依据。前者决定界面生成的内容能否成为真实工作流，后者决定开发者能否相信并控制正在运行的任务；回放调试、自然语言修改和开发者体验作为辅助判定：

- 高：核心两个维度均达到高档，回放调试与副作用隔离不低于中档，其余维度不低于中档。
- 中：核心两个维度均不低于中档，或其中一个维度为高档、另一个不低于中档，其余维度允许存在低档。
- 低：核心两个维度中至少一个为低档，或系统无法与真实 AET 工作流完成端到端对接。

## 任务十：Artifacts Reviewer（跨工件关联评审）

### 任务背景

AET 使用研发工件在不同 Agent 和不同阶段之间传递上下文。一次功能开发可能依次产生 Issue、RAS、RDS、DPS、代码变更、测试结果和验证报告。将这些结果固化为工件，有助于保存需求、设计、实现与验证依据，也为人工评审提供了基础。

但工件数量增加后，人工评审容易退化为在多个 Markdown 文件、代码 Diff 和测试报告之间来回查找。评审者看到一条需求时，需要自行判断它对应哪项设计决策、哪些开发任务、哪些代码以及哪条测试证据；发现问题后，评论通常又停留在某个文件或对话中，无法稳定传递给负责修改的 Agent。后续工件更新时，还可能出现评论已经解决但仍显示为待处理，或者原评论所针对内容已经变化却没有提示的情况。

Artifacts Reviewer 的目标不是替代人做最终评审，也不是重新实现需求分析、设计或代码审查能力，而是把现有工件及相关检查结果组织成可导航、可评论、可决策的评审视图。系统需要帮助评审者找到证据、记录判断、跟踪修改，并把结构化反馈传递回 AET 工作流。对于缺失或无法确认的关联，系统应明确标记不确定性，不能为形成完整链路而编造对应关系。

### 任务描述

需要实现面向 AET 研发工件的关联展示、人工评审与反馈回流能力，具体需求如下：

1. **多类工件接入**：应能够读取并展示一次 AET 研发任务中的 Issue、RAS、RDS、DPS、代码 Diff、测试结果和验证报告；应保留工件的原始路径、版本、生成阶段和其他可用元数据，使界面内容可以回到原始工件核实。

2. **跨工件关联视图**：应以需求、场景、设计决策、开发任务或验收条件等稳定标识组织工件关系，使评审者可以从一条上游要求导航到对应的设计、实现和验证证据；关联关系可以来自 AET 已有元数据、确定性规则、模型分析或人工补充，但必须标明来源。

3. **证据定位与不确定性呈现**：点击关联项时，应定位到具体工件段落、代码文件与位置、测试用例或结果记录；对缺失、冲突、低置信度或无法自动判断的关系，应明确展示状态和原因，不得将推测结果作为已确认事实呈现。

4. **辅助检查结果集成**：应能够接入 AET 已有或学生选择实现的需求一致性、设计检查、代码审查、测试验证等结果，并将问题关联到相应工件；本任务不要求重新实现所有检查算法，但应提供统一的问题查看和核实入口。

5. **结构化评审操作**：评审者应能够针对工件整体、具体条目或证据位置发表评论，并执行批准、驳回、请求修改、暂缓决定等操作；评审记录至少应包含目标、意见内容、状态、时间和对应工件版本。

6. **反馈路由与修改回流**：请求修改的意见应能够转换为结构化反馈，并传递给负责对应阶段或工件的 Agent；Agent 完成修改后，系统应展示修改前后差异，并将新版本与原始意见关联，供评审者确认是否解决。

7. **评论与版本生命周期**：工件发生变化后，应能够区分仍然适用、已经解决、需要重新确认和因目标内容变化而过期的评论；不得仅根据文件发生变化就自动关闭全部意见，也不得把针对旧版本的定位错误地附着到新版本无关内容上。

8. **评审进度与门禁**：应展示各工件和各项验收条件的评审状态、未处理意见及缺失证据；当工作流配置要求某阶段必须完成评审时，未满足批准条件的工件不能仅通过前端操作绕过门禁进入下一阶段。

9. **权限与审计**：如果系统支持多角色使用，应区分查看、评论、批准和管理等权限；所有影响评审结论或工作流推进的操作应保留审计记录。课程实现可以简化身份系统，但不得只在前端隐藏按钮而不做服务端检查。

10. **使用效果评估**：应使用包含预置问题的工件集合，对比 Artifacts Reviewer 与直接阅读分散文件时的问题发现率、评审完成时间、遗漏数量或错误关联数量，以验证跨工件视图是否实际改善评审过程。

### 验收方法

验收应覆盖以下方面，具体工件集合、预置问题和评审任务由学生自行设计与构造：

1. **工件接入与原文核验**：准备一条包含 Issue、RAS、RDS、DPS、代码、测试和验证报告的完整任务，验证各类工件能否正确载入；界面中的内容、版本和定位信息应能够与原始文件核对一致。

2. **跨工件关联准确性**：为测试工件预先标注需求、设计、开发任务、代码和测试之间的对应关系，验证系统建立的关联是否正确；应分别统计正确关联、遗漏关联和错误关联，并检查每条关联的来源标识。

3. **缺失与冲突场景验证**：构造需求无设计、设计无实现、代码无测试、验证结论与测试结果冲突，以及无法确定对应关系等场景，验证系统能否准确展示问题和不确定性，而不是自动补全不存在的证据。

4. **评审操作验证**：对工件整体、具体条目和代码位置分别发起评论、批准、驳回、请求修改和暂缓决定，验证记录目标、状态、版本和审计信息是否正确；无权限用户不得通过直接调用接口完成批准。

5. **反馈回流验证**：选择若干请求修改意见，将其发送给不同阶段的 Agent，验证反馈是否路由到正确对象；Agent 修改工件后，验证界面能否展示差异，并由评审者判断意见是否解决。

6. **版本与评论生命周期验证**：连续修改同一工件，构造内容未变化、位置移动、内容被修改和目标被删除等情况，验证评论是否分别保持有效、重新定位、等待复核或标记过期；原始评论和历史版本仍应可追溯。

7. **评审门禁验证**：配置一个必须通过人工评审才能进入下一阶段的流程，验证存在未解决阻塞意见或缺少批准时无法推进；完成必要评审后，工作流应能够正常继续，且批准依据可以被核实。

8. **开发者体验验证**：组织参与者分别使用 Artifacts Reviewer 和原始文件方式审查同一批包含预置问题的工件，记录问题发现率、误报、遗漏、完成时间和操作步骤；应说明参与者背景、训练过程及可能影响结果的因素。

9. **AET 集成验证**：在真实 AET 研发任务中完成“载入工件—建立关联—发起评审—反馈给 Agent—更新工件—确认解决—通过门禁”的端到端流程，验证评审结果能够实际影响后续工作流，而非只保存在独立页面中。

验收时应明确说明 AET 版本、工件来源、人工标注方式、问题注入方法、评审角色和实验条件，并针对上述要求逐一说明满足情况及依据。

### 完成度标准

对学生的任务完成度按高、中、低三档评估，沿用验收方法中的五个维度，逐项判断达成程度，再综合得出总体档位。

**跨工件关联与证据定位**

- 高：能够稳定接入主要 AET 工件，需求、设计、实现和验证之间的关联准确、来源清晰；评审者可以定位到具体段落、代码或测试证据，对缺失和不确定关系有明确标识。
- 中：能够接入主要工件并建立大部分关联，但存在一定的遗漏或错误，部分关系只能定位到文件级，或不确定性标识不完整。
- 低：只能并排展示文件，缺少实质性的跨工件关联，关联结果大量错误，或无法回到原始证据核实。

**评审操作与权限可靠性**

- 高：评论、批准、驳回、请求修改和暂缓等操作完整可用，评审目标、版本和审计记录准确；权限在服务端有效执行，必要评审门禁无法绕过。
- 中：主要评审操作可用，但部分粒度、审计或权限能力不完整，或在少数情况下需要人工修正状态。
- 低：评审操作仅停留在界面展示，记录无法准确关联目标和版本，权限只由前端控制，或门禁可以被轻易绕过。

**反馈回流与问题处理闭环**

- 高：请求修改意见能够准确路由给对应 Agent，修改结果和差异可见，评审者可以基于新证据确认是否解决，完整过程可追溯。
- 中：反馈能够传递并触发修改，但路由、差异展示或解决确认中的部分环节不完整，仍需人工补充上下文。
- 低：评论只能保存在评审系统中，无法传递给 Agent 或影响工作流，修改后也无法判断原问题是否解决。

**版本与评论生命周期**

- 高：能正确处理内容不变、位置移动、内容修改和目标删除等情况，评论状态与目标版本一致，历史意见和工件均可追溯。
- 中：支持基本版本对比和评论状态管理，但在复杂修改下可能错误迁移或关闭部分评论。
- 低：工件更新后评论普遍丢失、错位或被无条件关闭，无法追溯评审所依据的版本。

**评审效果与真实集成**

- 高：在包含预置问题的对比实验中，问题发现率、完成时间或遗漏数量等多个指标体现出可复现的改善，并在真实 AET 工作流中完成端到端评审和门禁验证。
- 中：完成了真实 AET 对接，并在至少一个评审指标上有所改善，但数据规模较小、改进不稳定，或部分流程仍依赖人工操作。
- 低：主要为静态工件浏览器，未验证评审效果，或评审结果无法实际进入 AET 工作流。

**综合定档规则**

以“跨工件关联与证据定位”和“反馈回流与问题处理闭环”两个维度作为核心判定依据。前者决定评审者看到的关系是否可信，后者决定评审意见能否真正改变后续研发结果；评审操作、版本管理和使用效果作为辅助判定：

- 高：核心两个维度均达到高档，其余维度不低于中档。
- 中：核心两个维度均不低于中档，或其中一个维度为高档、另一个不低于中档，其余维度允许存在低档。
- 低：核心两个维度中至少一个为低档，或系统无法完成评审意见进入 AET 工作流并得到修改结果的闭环。

## 任务十一：Architecture Explorer（架构上下文与围栏交互浏览）

### 任务背景

AET 的架构上下文用于描述代码库的模块职责、依赖关系、公共接口和边界约束，围栏则结合当前研发任务限定允许、禁止或有条件修改的范围。这些信息能够帮助 Agent 在修改代码前理解项目结构，并减少跨层调用、反向依赖、循环依赖和受保护接口被意外修改等问题。

架构上下文和围栏即使已经生成，也不一定容易被开发者使用。面对较大的代码库，开发者需要在模块文档、依赖矩阵、开发计划和代码文件之间查找，才能回答“当前任务为什么不能修改这个文件”“某个接口改变后可能影响哪些模块”“这条围栏规则来自架构约束还是本次开发计划”等问题。当依赖关系或任务边界只以长文本和表格呈现时，人工判断的时间和误判概率都会随模块数量增加。

围栏还包含人工决策。某些任务在实施过程中可能发现原计划范围不足，需要申请修改受保护模块。开发者不仅需要看到当前边界，还需要理解规则来源、提交突破原因、查看审批结果，并确认批准后的边界已经同步到后续开发和评审环节。如果界面只改变颜色而没有与底层规则和审批记录保持一致，可能让使用者误以为某项修改已经获得授权。

Architecture Explorer 的目标是消费 AET 已有架构上下文和围栏结果，为开发者提供可查询、可解释、可追溯的交互视图。本任务不要求重新实现代码库架构分析或围栏生成算法，重点是保证可视化结果与底层事实一致，并帮助开发者完成影响判断和围栏审批。

### 任务描述

需要实现面向 AET 架构上下文和围栏信息的交互浏览、影响查询与审批能力，具体需求如下：

1. **架构数据接入**：应能够读取 AET 已有的模块清单、模块职责、依赖关系、公共接口、边界约束及其他可用架构上下文；应保留数据来源、生成版本和对应代码基线，使界面内容能够与原始文档或代码核实。

2. **多层次架构浏览**：应以图形方式展示模块和依赖关系，并支持从全局视图逐步进入模块、接口、文件或符号等可用粒度；应提供搜索、过滤、折叠、展开、路径高亮和局部视图，避免模块数量增加后只能查看一张无法操作的完整大图。

3. **依赖证据与规则解释**：点击模块节点、依赖边或边界规则时，应能够查看其来源依据，如配置、导入关系、接口定义、架构文档或人工确认记录；系统应区分代码事实、文档声明、工具推断和人工判断，不能把来源不同的信息混为同一置信级别。

4. **当前任务围栏叠加**：应根据当前研发任务展示允许修改、禁止修改和有条件修改的文件或模块范围；如果底层数据支持只读、限制修改内容等更细粒度规则，界面也应正确呈现；使用者应能够区分长期架构约束与本次任务临时边界，并查看每条规则的来源和生效范围。

5. **变更影响查询**：选择一个模块、接口、文件或符号后，应能够展示其直接和间接受影响对象、可能传播的依赖路径以及相关围栏限制；查询结论必须关联到实际依赖数据，不得仅由模型生成无法核实的影响描述。

6. **架构版本与变更对比**：应支持比较两个架构上下文或代码基线之间的模块、依赖、接口和边界变化，区分新增、删除和修改；当当前围栏基于过期架构版本时，应明确提示，不得继续将旧边界显示为当前事实。

7. **围栏突破申请与审批**：当开发者确需修改禁止或有条件修改的对象时，应能够从界面发起突破申请，填写修改目标、原因、影响和相关证据；审批结果应记录批准或拒绝的对象、范围、条件、人员和时间，并同步更新当前任务的有效边界。

8. **状态一致性与防绕过**：界面中的围栏状态、审批状态和最终有效边界应与 AET 后台保持一致；前端颜色或本地状态变化不能直接视为授权，未经批准的修改仍应被后续检查识别；多个用户或视图同时操作时，应处理版本冲突并避免后提交结果静默覆盖先前审批。

9. **规模适应性**：系统应能够处理不同规模的架构数据；随着模块和依赖数量增加，搜索、过滤、局部展开和影响查询仍应保持可用；学生应说明选用的数据规模，并给出加载时间、交互响应时间或查询时间等测量结果。

10. **使用效果评估**：应设计固定的架构理解、影响判断和围栏判断任务，对比 Architecture Explorer 与直接阅读架构文档、依赖矩阵和开发计划时的正确率、完成时间和误判数量，以验证交互视图是否真正帮助开发者做出判断。

### 验收方法

验收应覆盖以下方面，具体代码库、架构数据、任务围栏和测试问题由学生自行设计与构造：

1. **架构数据一致性验证**：选择一个具有已知模块和依赖关系的项目，将 Architecture Explorer 中的节点、依赖和接口信息与 AET 架构上下文及代码证据逐项核对；界面不得新增底层数据中不存在且未标记为推断的关系。

2. **分层浏览与证据定位验证**：从全局架构进入指定模块，再定位到接口、文件或其他可用证据；验证搜索、过滤、局部视图和路径高亮是否能够帮助使用者找到目标，并检查每条关键关系是否能够回到原始来源。

3. **任务围栏展示验证**：准备多组包含允许、禁止和有条件修改对象的任务围栏，验证界面分类、来源、生效范围和条件是否与后台一致；同时存在长期架构约束与临时任务规则时，应能够准确区分。

4. **影响查询准确性验证**：预先标注若干模块、接口或文件的直接与间接影响范围，验证系统返回的影响对象和传播路径；应分别统计遗漏和错误结果，并核验查询结论引用的依赖证据。

5. **版本变化验证**：在代码库中增加、删除或修改模块依赖和公共接口，重新生成或导入新版本架构上下文，验证变更对比是否准确；使用旧版本围栏时，系统应识别基线不一致并提示重新确认。

6. **围栏突破流程验证**：分别对禁止修改和有条件修改对象发起申请，执行批准、附条件批准和拒绝等操作，验证申请记录、审批信息和最终有效边界；未经批准时，界面和后台均不得将目标标记为允许修改。

7. **并发与防绕过验证**：构造两个使用者同时处理同一申请、旧页面提交过期审批结果以及绕过前端直接调用接口等场景，验证系统能否发现版本冲突、拒绝无效操作并保留审计记录。

8. **规模适应性验证**：使用至少两种规模的架构数据验证首次加载、搜索、过滤、局部展开和影响查询；当完整图不可读时，应证明使用者仍能通过局部视图完成指定任务，而不是只报告页面成功渲染。

9. **开发者体验验证**：组织参与者分别使用 Architecture Explorer 和原始文档方式完成模块定位、依赖路径查询、影响判断和围栏判断任务，记录正确率、完成时间、误判和求助次数，并说明参与者背景及实验限制。

10. **AET 集成验证**：在真实 AET 项目中完成“载入架构上下文—选择当前任务—查看有效围栏—查询修改影响—发起突破申请—审批—验证边界同步”的端到端流程，确保系统消费和更新的是 AET 的真实数据。

验收时应明确说明 AET 版本、项目代码基线、架构上下文来源、围栏数据、人工标注方法、数据规模和参与者背景，并针对上述要求逐一说明满足情况及依据。

### 完成度标准

对学生的任务完成度按高、中、低三档评估，沿用验收方法中的五个维度，逐项判断达成程度，再综合得出总体档位。

**架构与围栏数据一致性**

- 高：模块、依赖、接口和围栏状态均与 AET 底层数据保持一致，能够标明代码事实、文档声明、工具推断和人工判断的来源；架构或围栏版本过期时能够准确提示。
- 中：主要架构和围栏信息基本一致，但部分来源、版本或细粒度规则展示不完整，存在少量需要人工核实的错误。
- 低：可视化内容与底层数据经常不一致，存在大量无法解释来源的关系，或旧版本信息被当作当前事实展示。

**架构浏览与证据追溯**

- 高：支持从全局到局部的稳定导航，搜索、过滤和路径高亮可用；关键节点、依赖和规则均能定位到具体原始证据。
- 中：基本浏览和搜索可用，但在复杂关系下导航效率下降，或部分信息只能追溯到文档或文件级。
- 低：主要呈现静态大图，难以定位目标，关键关系无法回到原始代码、配置或文档核实。

**变更影响判断能力**

- 高：能够基于实际依赖数据准确展示直接和间接影响范围及传播路径，对人工标注案例的遗漏和错误较少，结论均有可核实依据。
- 中：能够完成主要影响查询，但复杂路径下存在一定遗漏或误报，部分结论的依据不够具体。
- 低：影响结果主要为无证据的文本描述，无法稳定识别直接依赖或传播路径，结果不足以支持修改决策。

**围栏突破与状态控制**

- 高：申请、批准、附条件批准、拒绝和边界同步流程完整，审批对象与范围准确；并发和绕过场景受到服务端控制，所有关键操作可审计。
- 中：基本申请和审批流程可用，但对附加条件、并发冲突、版本控制或审计的支持不完整。
- 低：审批主要是前端状态变化，未经批准也可能显示或实际获得修改权限，或审批记录无法核实。

**规模、使用效果与真实集成**

- 高：在不同规模数据下，局部浏览和影响查询保持可用；对比实验在正确率、完成时间或误判数量中的多个指标上体现出可复现的改善，并完成真实 AET 端到端集成。
- 中：中小规模下基本可用并完成 AET 对接，在至少一个使用效果指标上有所改善，但大型数据或复杂路径下体验明显下降。
- 低：只在少量静态示例上可用，模块数量增加后无法完成指定任务，或没有接入真实 AET 架构上下文和围栏数据。

**综合定档规则**

以“架构与围栏数据一致性”和“变更影响判断能力”两个维度作为核心判定依据。前者决定使用者看到的边界是否可信，后者决定界面能否支持实际修改决策；架构浏览、审批控制和使用效果作为辅助判定：

- 高：核心两个维度均达到高档，其余维度不低于中档。
- 中：核心两个维度均不低于中档，或其中一个维度为高档、另一个不低于中档，其余维度允许存在低档。
- 低：核心两个维度中至少一个为低档，或系统未使用真实 AET 架构上下文和围栏数据。
